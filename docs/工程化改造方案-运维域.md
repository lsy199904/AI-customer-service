## 0. 先明确三条边界（否则方案会落空）

### 0.1 应用启动时仍会建表

不改 `app/` 的前提下，以下运行期 DDL 无法移除：

| 位置 | 行为 |
|---|---|
| `app/core.py` `Service.__init__` | `CREATE TABLE IF NOT EXISTS sessions/messages/rate_limits/tenant_message_limits/global_rag_daily_limits/workflow_runs` + `ALTER TABLE messages ADD COLUMN seq` |
| `app/rag.py` `DocumentStore.__init__` | `CREATE TABLE IF NOT EXISTS rag_state/rag_documents/rag_revisions/rag_chunks/rag_events/rag_embedding_cache` |
| `app/workflow.py` `SupportWorkflow.__init__` | `PostgresSaver.setup()`，按 `checkpoint_migrations` 版本补建检查点表 |
| `app/deployment.py` `claim()` | 归属表 `assistant.external_deployment` 不存在时创建并写入 |

**结论**：Flyway 无法成为「唯一执行者」，只能成为**唯一变更来源**。应用启动时的建表必须退化为**幂等空操作**，并由契约测试保证两者结构完全一致。

### 0.2 知识入库仍是应用命令

`python manage.py ingest` 内部完成「解析 → 切片 → Embedding → 写 PG → 写 Milvus → 切换 revision」，且 `MilvusVectors.ensure()` 会在 upsert 时**顺带建集合**。不改 `app/` 就无法把向量写入从这段代码里拆出去。

**结论**：本轮拆的是**任务边界**（独立 Job、独立配置、独立权限、独立触发），不是代码调用链。集合初始化可以真正独立（预建集合后 `ensure()` 变成 no-op）；向量写入只能以「专用 Job 调用同一入口」的方式独立。

### 0.3 因此本方案分两层交付

| 层级 | 本轮可完成 | 依赖 app 改动 |
|---|---|---|
| 资产层：SQL/集合定义/配置/镜像/Job 与代码分离 | ✅ 全部 | 否 |
| 执行层：迁移、集合初始化、入库、校验独立触发 | ✅ 全部 | 否 |
| 代码层：app 不再执行任何 DDL、不再建集合 | ❌ | 是（见 §9 交接项） |

## 2. 目标原则

1. **单一事实源**：同一结构只允许一处定义。PG 以 `../database/archive/postgres` 为准，Milvus 以 `database/milvus/contract.json` 为准。
2. **资产与运行时分离**：应用镜像不携带迁移 SQL；迁移镜像不含应用代码；知识任务不加载 LLM/Rerank 凭证。
3. **声明式 + 幂等**：所有任务可重复执行，第二次执行必须是 no-op。
4. **只前进、可回退**：数据库不 undo，应用镜像可回退；破坏性变更拆两次发布。
5. **最小权限**：migrator 用独立 DDL 账号；知识任务只拿 Embedding/Milvus 凭证。

## 4. PostgreSQL 工程化方案

### 4.1 职责边界

| 数据类别 | 归属 | 存放位置 | 执行者 | 示例 |
|---|---|---|---|---|
| 结构 DDL | 运维 | `migrations/V__` | Flyway | 建表、加列、建索引、约束 |
| 一次性数据修复/回填 | 运维 | `migrations/V__`（带工单号） | Flyway | 修历史脏数据、补默认值 |
| 参考数据/字典/授权 | 运维 | `repeatable/R__` | Flyway（校验和变化时重跑） | 只读角色授权、枚举字典 |
| 部署归属凭证行 | 运维 | `V1.0.0` + 占位符 | Flyway；应用只读校验 | `external_deployment` |
| 业务运行数据 | **应用** | — | 应用运行时 | `sessions`、`messages`、配额、`rag_*` |

**硬规则**：`rag_*` 表里的文档、切片、向量缓存属于「入库管道产物」，由知识任务写入；但它们的**结构**只能由 Flyway 定义。两者不冲突，边界是「结构 vs 数据」。

### 4.2 目录组织与命名

```text
database/postgres/
├── conf/flyway.conf
├── migrations/
│   ├── V1.0.0__baseline.sql
│   └── V1.2.0__add_ops_milvus_registry.sql
├── repeatable/
│   └── R__01_readonly_grants.sql
├── callbacks/
│   ├── beforeMigrate__verify_identity.sql
│   └── afterMigrate__health.sql
└── checks/
    └── contract_expected.sql
```

`flyway.conf` 关键项：

```properties
flyway.locations=filesystem:migrations,filesystem:repeatable,filesystem:callbacks
flyway.schemas=assistant,knowledge
flyway.defaultSchema=assistant
flyway.table=flyway_schema_history
flyway.validateOnMigrate=true
flyway.cleanDisabled=true
flyway.baselineOnMigrate=false
flyway.outOfOrder=false
flyway.ignoreMigrationPatterns=*:future
flyway.connectRetries=10
```

命名规则：

| 类型 | 规则 | 说明 |
|---|---|---|
| 版本化 | `V<major>.<minor>.<patch>__<snake_case>.sql` | 与 app SemVer 对齐；一个发布 PR 只允许一个 V 文件 |
| 可重复 | `R__<两位序号>_<desc>.sql` | 必须幂等（`ON CONFLICT`/`IF NOT EXISTS`）；校验和变化即重跑 |
| 回调 | `beforeMigrate__<desc>.sql`、`afterMigrate__<desc>.sql` | 只做校验/体检，不写业务数据 |

已应用的 `V__` 文件**永不修改**。校验和不符时只能用 `flyway repair` 修 history 元数据，不能改 SQL。

### 4.3 版本与迁移管理

**版本链**

```text
V1.0.0（基线：全量结构 + 归属凭证行）
  └─ V1.2.0（新增 ops.milvus_collections 登记表，可选）
       └─ V1.3.0（业务新增列，additive）
```

**允许 / 禁止**

| 允许 | 禁止 |
|---|---|
| `CREATE TABLE`、`ADD COLUMN`（可空或带默认） | `DROP TABLE/COLUMN`、`RENAME`（必须拆两次发布） |
| `CREATE INDEX`（维护窗口内普通建索引） | 修改已应用迁移文件 |
| `INSERT ... ON CONFLICT`（参考数据） | 在 Flyway 中写业务运行数据 |
| 带 `WHERE` 与前后计数断言的回填 | 无 `WHERE` 的全表 `UPDATE` |
| `COMMENT ON`、授权 | `TRUNCATE`、`DELETE` 无工单 |

**破坏性变更走 expand/contract**：

1. `V1.x`：新增列/新表，应用双读或忽略 → 发布；
2. `V1.y`：回填 + 校验；
3. `V2.0`：删除旧列/旧表（需确认 N-1 镜像已下线）。

**CI 四道门（缺一不可）**

| 门 | 内容 | 失败即阻断 |
|---|---|---|
| G1 语法与校验 | `flyway validate` + 重复版本号检测 | 是 |
| G2 全新建库 | 空 PG 执行 `migrate`，跑 `checks/health.sql` | 是 |
| G3 升级兼容 | 起 N-1 版本库 → `migrate` 到 head → 再跑一遍应用启动 | 是 |
| G4 结构契约 | Flyway 建库 vs 应用自建库，`pg_dump --schema-only` 归一化后 diff 为零 | 是 |

**G4 是本方案的核心安全网**，具体做法见 §4.5。

### 4.4 执行入口

| 场景 | 入口 | 命令 | 说明 |
|---|---|---|---|
| 本地/研发 | `scripts/db.sh` | `./scripts/db.sh migrate` | 通过 compose 起 migrator 容器，复用同一镜像 |
| CI | `compose.ci.yaml` + `db.sh` | `./scripts/db.sh check` | G1–G4 全跑 |
| 生产（默认） | Deployment 的 `db-migrate` Init 容器 | `kubectl apply -k overlays/prod` | **保留**：保证迁移先于应用进程，天然串行、失败即 rollout 失败 |
| 生产（按需/破窗） | `job-db-migrate.yaml` | `kubectl apply -f ... && kubectl wait` | 演练、修复、手工 baseline 后的补迁移 |
| 存量接入 | `job-db-baseline.yaml` | 一次性 `baseline` | 前后各一次 `pg_dump` |

`scripts/db.sh` 子命令约定：

```bash
./scripts/db.sh info        # 当前版本 + 待执行列表（只读）
./scripts/db.sh validate    # 校验和/顺序
./scripts/db.sh migrate     # 执行迁移
./scripts/db.sh baseline    # 仅存量库，一次性
./scripts/db.sh repair      # 仅修 history 元数据
./scripts/db.sh check       # G4 契约 diff
./scripts/db.sh psql        # 只读排查入口
```

**为什么生产仍保留 Init 容器**：应用不能改，启动即建表；若迁移改成完全独立的 Job，一旦 Job 未执行或失败而 Deployment 先滚动，应用会在旧结构上启动并静默建表，直接制造漂移。Init 容器是当前约束下风险最低的「顺序保证」。它使用的镜像不含任何应用代码，已满足「与 app 解耦」的资产要求。

### 4.5 与 app 运行期 DDL 的兼容契约（关键）

**目标**：证明 `Flyway 建出的结构` 与 `app 自建的结构` 完全一致。

**步骤（CI 中自动执行）**

```bash
# A. Flyway 建库
createdb contract_a
FLYWAY_URL=jdbc:postgresql://.../contract_a ./scripts/db.sh migrate
pg_dump --schema-only --schema=assistant --schema=knowledge contract_a > /tmp/a.sql

# B. 应用自建库（只触发建表，不启动 HTTP）
createdb contract_b
DATABASE_URL=postgresql://.../contract_b \
ANSWER_MODE=extractive RETRIEVAL_BACKEND=lexical VECTOR_BACKEND=sqlite \
AUTH_SECRET=$(python3 -c "import secrets;print(secrets.token_urlsafe(48))") \
python3 -c "from app.core import Service,Settings; s=Service(Settings()); s.close()"
pg_dump --schema-only --schema=assistant --schema=knowledge contract_b > /tmp/b.sql

# C. 归一化后 diff
python3 tests/ops/normalize_schema.py /tmp/a.sql /tmp/b.sql | diff -u - /dev/null
```

**归一化必须剔除**：`flyway_schema_history`、`external_deployment`（应用不建）、`SET/SELECT pg_catalog`、`OWNER TO`、`COMMENT`、`GRANT/REVOKE`、空行与排序差异。

**必须保留比对**：表名、列名与顺序、类型、可空性、默认值、主键/唯一约束、索引名与列、序列归属。

**门禁策略**：
- G4 失败 → 阻断合并，由运维补 `V__` 修正（不得改基线）；
- 每次 app 升级（同事合并新代码）自动重跑 G4；
- 结果写入 `../database/archive/postgres`：`app commit ↔ schema version ↔ 契约结果`。

**为什么不用「让应用跳过建表」来简化**：需要改 `app/`，本轮不允许。等 §9 的交接项落地后，G4 可从「diff」升级为「应用只读断言 schema 版本」。

### 4.6 配置与凭证

| 配置 | 来源 | 使用者 | 说明 |
|---|---|---|---|
| `FLYWAY_URL` | Secret | migrator | JDBC 格式，由 `scripts/dburl.py` 从 `DATABASE_URL` 生成 |
| `FLYWAY_USER/PASSWORD` | Secret（或 URL 内嵌） | migrator | 建议独立 DDL 账号，不用业务账号 |
| `FLYWAY_PLACEHOLDERS_DEPLOYMENT_ID` | ConfigMap | migrator | 与 app 的 `DEPLOYMENT_ID` 完全一致 |
| `FLYWAY_PLACEHOLDERS_MILVUS_URI/DATABASE/PREFIX` | ConfigMap | migrator | `uri` 需 `rstrip('/')`；缺失即失败 |

**权限模型**：

```text
PG:
  titu_ddl    → 库 OWNER 或具备 CREATE on schema；仅 migrator 使用
  titu_app    → 仅 DML（SELECT/INSERT/UPDATE/DELETE）+ 序列 USAGE；应用使用
  titu_ro     → 只读；排查/BI 使用（由 R__01 授权）
Milvus:
  app token   → 读写当前库
  admin token → 仅 ensure/gc 任务使用，且不入应用配置
```

> 注意：当前 `app/cloud.py` 要求业务账号具备目标库 `CREATE` 权限（应用要建 schema）。在 app 改动前，`titu_app` 仍需要 `CREATE`，无法收窄到纯 DML。这是 §9 的交接项之一。

### 4.7 存量环境基线（一次性）

```bash
# 1. 停写（Recreate 发布窗口）
kubectl -n app-zone scale deploy/titu-assistant --replicas=0

# 2. 快照
pg_dump -Fc "$DATABASE_URL" > backup-$(date +%F-%H%M).dump

# 3. 核对归属凭证行与当前环境一致
psql "$DATABASE_URL" -c "SELECT metadata FROM assistant.external_deployment;"

# 4. 基线（只登记版本，不执行 SQL）
```

## 5. Milvus 与知识入库方案

### 5.1 当前耦合点

```text
manage.py ingest
  └─ app.rag.ingest_documents
       ├─ parse_document / pdf_media.extract
       ├─ EmbeddingClient.embed
       ├─ DocumentStore（写 PG revisions/chunks）
       ├─ MilvusVectors.ensure()   ← 建集合（DDL 藏在应用里）
       ├─ MilvusVectors.upsert()   ← 写向量
       └─ 单事务切换 current_revision
```

三个问题：
1. 集合 DDL 由应用在入库时顺带执行，运维无法独立预检；
2. 入库绑在 app Deployment 的 Init 容器上，Embedding 故障 = 发版失败；
3. 集合定义存在三份拷贝（脚本、应用、文档），无一致性门禁。

### 5.2 任务拆分

| 任务 | 镜像 | 输入 | 输出 | 幂等性 | 失败影响 |
|---|---|---|---|---|---|
| `db-migrate` | `db-migrate` | SQL + 占位符 | schema 版本 | ✅ | 阻断发布 |
| `milvus-ensure` | `knowledge-tools` | `contract.json` + `MILVUS_*` + Embedding 维度 | 集合就绪或结构核对通过 | ✅ 已存在则只校验，不修改 | 阻断入库 |
| `knowledge-ingest` | `assistant`（同源） | `knowledge_sources/` + PG + Milvus | PG 修订 + 向量 + 激活指针 | ✅ 指纹不变时 no-op | 阻断发布（可选） |
| `knowledge-verify` | `knowledge-tools` | PG + Milvus | JSON 校验报告 | ✅ 只读 | 阻断发布 |
| `milvus-gc` | `knowledge-tools` | 集合列表 + 保留策略 | 候选清单 / 删除结果 | ⚠️ 必须显式 `--confirm` | 不影响在线 |

**为什么 ingest 复用 assistant 镜像**：解析器版本、切片参数、Embedding 调用方式共同决定 `revision` 与 `fingerprint`。换镜像等于引入第二套实现，必然漂移。**任务独立 ≠ 镜像必须不同**；这里用「同源镜像 + 独立 Job + 独立配置/权限」实现解耦。

**集合初始化如何真正独立**：`app/vectors.py:ensure()` 的逻辑是「存在则校验维度，不存在则创建」。`milvus-ensure` 预先按同一 schema 建好集合后，应用侧 `ensure()` 自然退化为一次 `describe_collection`，不再执行任何 DDL。这就是本轮能做到的「初始化与 app 解耦」。

### 5.3 触发方式与发布时序

```text
release.sh（或 CI）
  ├─ 1. preflight        ./scripts/doctor.sh config   # 配置齐全、两处 MILVUS_*/EMBEDDING_* 一致
  ├─ 2. db-migrate       Init 容器 / job-db-migrate   # 结构就绪
  ├─ 3. milvus-ensure    job-knowledge-ensure         # 集合就绪（不写数据）
  ├─ 4. knowledge-ingest job-knowledge-ingest         # 增量入库（写 PG + Milvus）
  ├─ 5. knowledge-verify job-knowledge-verify         # 只读一致性校验
  └─ 6. app rollout      kubectl apply -k overlays/<env>
```

| 触发方式 | 任务 | 说明 |
|---|---|---|
| 发版流水线 | ensure → ingest → verify | 顺序执行，任一步失败即停止，不滚动应用 |
| 每日定时 | `CronJob knowledge-ingest`（02:00） | 增量；指纹不变时秒级 no-op |
| 手动 | `./scripts/knowledge.sh ingest` | 内容更新、紧急补录 |
| 每月定时 | `CronJob milvus-gc`（dry-run） | 只输出候选，人工确认后删除 |
| 首次部署 | release.sh 全链路 | 空库 → 全量 → 校验 → 启动 |

**关键顺序约束**：`knowledge-verify` 必须在应用滚动前完成。应用 `/ready` 在知识为空时返回 503，而 `startupProbe` 预算 10 分钟；若先起应用再入库，Pod 会反复重启。因此**不允许**把 ingest 改成与应用并行的独立 Job 后就直接 `apply`。

### 5.4 配置管理

按角色拆分，避免知识任务拿到 LLM 凭证：

| 配置对象 | 键 | 使用者 |
|---|---|---|
| `titu-common-config`（ConfigMap） | `DEPLOYMENT_ID`、`MILVUS_URI`、`MILVUS_DATABASE`、`MILVUS_COLLECTION`、`MILVUS_INDEX_TYPE`、`EMBEDDING_PROVIDER/URL/MODEL/REVISION`、`KNOWLEDGE_SOURCE_DIR`、`PDF_MEDIA_*`、`LOG_*` | 全部 |
| `titu-app-secret`（Secret） | `DATABASE_URL`、`AUTH_SECRET`、`MODEL_API_KEY`、`RERANK_API_KEY`、`OPERATIONS_TOKEN` | app |
| `titu-knowledge-secret`（Secret） | `EMBEDDING_API_KEY`、`MILVUS_TOKEN` | ingest/ensure/verify |
| `titu-db-secret`（Secret） | `FLYWAY_URL`、`FLYWAY_USER/PASSWORD` | migrator |

**一致性校验**：`scripts/doctor.sh config` 逐项比对 app 与知识任务实际生效的 `MILVUS_*`、`EMBEDDING_*`。任何一项不同即失败——否则会出现「应用查旧集合、任务写新集合」的静默故障。

`contract.json` 固定以下内容，作为 Milvus 侧唯一事实源：

```json
{
  "pipeline_version": "documents-v2",
  "text_version": "retrieval-text-v2",
  "chunk_chars": 1000,
  "overlap_chars": 100,
  "collection_prefix_env": "MILVUS_COLLECTION",
  "fields": [
    {"name": "id", "type": "VARCHAR", "max_length": 80, "primary": true},
    {"name": "document_id", "type": "VARCHAR", "max_length": 80},
    {"name": "revision", "type": "VARCHAR", "max_length": 64},
    {"name": "vector", "type": "FLOAT_VECTOR"}
  ],
  "index": {"type": "HNSW", "metric": "COSINE", "M": 16, "efConstruction": 128},
  "consistency": "Strong"
}
```

CI 断言：`tests/ops/test_milvus_contract.py` 读取 `app.ingestion.PIPELINE_VERSION`、`app.retrieval.TEXT_VERSION`、`app.rag.RAGSettings().chunk_chars/overlap_chars`，与 `contract.json` 比对。**只导入、不修改**，用于捕获同事升级流水线版本但运维未同步的情况。

### 5.5 指纹与集合命名（运维必须知道的规则）

集合名 = `MILVUS_COLLECTION + "_" + fingerprint[:16]`，指纹取自：

```text
sha256(json([
  PIPELINE_VERSION, TEXT_VERSION,
  embedding_provider, embedding_url, embedding_model, embedding_revision,
  chunk_chars, overlap_chars
]))
```

| 变更项 | 是否产生新集合 | 是否需 `ingest --rebuild` | 是否等同新部署（需新库） |
|---|---|---|---|
| `EMBEDDING_MODEL` / `EMBEDDING_REVISION` / `EMBEDDING_PROVIDER` | 是 | 是 | 否（旧集合保留可回退） |
| `EMBEDDING_URL`（含端口） | 是 | 是 | 否 |
| 切片参数（代码内固定，升级 app 时可能变） | 是 | 是 | 否 |
| `MILVUS_COLLECTION` 前缀 | 是（名字变） | 是 | **是**（`external_deployment.milvus_prefix` 校验失败） |
| `MILVUS_TOKEN` / `MILVUS_INDEX_TYPE` | 否 | 否 | 否（但索引类型变更会导致 ensure 校验失败） |
| 知识文档内容变更 | 否（revision 变） | 增量即可 | 否 |

**结论**：`MILVUS_COLLECTION` 一旦投入生产不可修改；Embedding 三项变更必须走「新集合 + rebuild + 观察 + 延迟 GC」。

### 5.6 存储与共享卷（容易踩的坑）

`pdf_media.extract` 会把 PDF 图片落到 `PDF_MEDIA_DIR`，应用 `MediaCatalog.include_generated()` 从同一目录读取并提供 `/media/...`。当前 Init 容器与应用同 Pod 共享 `var` PVC，所以没问题。

拆成独立 Job 后：
- Job Pod 可能调度到另一节点，`ReadWriteOnce` PVC 无法同时挂载 → 入库失败或应用读不到图；
- 缓解方案（按优先级）：
  1. **RWX 存储**（NFS/CephFS）挂 `var/pdf_media`；
  2. Job 加 `nodeAffinity` 固定到应用所在节点，继续用 RWO；
  3. 长期：pdf 图片外置对象存储，应用只存 URL（需要 app 改动，列为后续项）。

推荐短期方案 2，中期方案 1，长期方案 3。

### 5.7 校验与回收

`verify.py` 只读检查：
1. PG `rag_state.fingerprint` 非空且与当前计算值一致；
2. 集合名 == `前缀_指纹前16位`；
3. `rag_documents` 中 `active=1` 的文档数 > 0；
4. 当前 revision 的 chunk 数 == Milvus 集合实体数（按 `document_id+revision` 过滤 count）；
5. 取 PG 中一条已存向量做 `search`，命中 id 必须包含自身。

`gc_collections.py` 策略：
- 默认 `--dry-run`，只列出「同前缀、非当前指纹」的集合；
- 删除必须 `--confirm --collection <完整名>`，一次一个；
- 禁止删除当前集合、禁止按时间自动删除；
- 建议保留 ≥ 7 天（覆盖一次回滚窗口）。

## 8. 回滚策略

**总原则**：数据库只前进，应用可回退；回退能力依赖「迁移兼容 N-1」纪律。

| 场景 | 动作 | 数据影响 | 备注 |
|---|---|---|---|
| 迁移执行失败 | Flyway 单迁移事务回滚，`history` 无成功行；修 SQL 后重跑 | 无 | 禁止手工改 `flyway_schema_history` |
| 迁移成功、应用异常 | `kubectl rollout undo deploy/titu-assistant` | schema 保持 | 旧镜像 `migrate` 因 `*:future` 通过并 no-op |
| 迁移本身写错数据 | 不回滚 schema；新增 `V__fix` 正向修复 | 可控 | 紧急时停写 + 从 `pg_dump` 恢复 |
| baseline 误操作 | 从发布前 `pg_dump -Fc` 恢复 | 回到快照点 | baseline 前强制快照是硬要求 |
| 知识入库失败 | 旧 revision 仍为 active，服务不受影响；重跑 ingest | 无 | 因为先写向量/切片、后切指针 |
| 新集合维度/指纹错误 | 恢复 Embedding 配置到旧值 → 旧集合仍可用 | 无 | 错误集合人工确认后删除 |
| 应用回退到 N-1 | `rollout undo`；数据库保留新列（additive） | 无 | 若新列 NOT NULL 无默认，则不可回退——迁移规范禁止 |
| 配置错误（prefix/URI） | 恢复 ConfigMap/Secret；不要改凭证行 | 无 | 归属校验会先拦住 |
| 镜像供应链问题 | 回退到上一 digest | 无 | 生产 overlay 引用 digest，不打浮动 tag |

**不可回退的操作（必须走变更窗口 + 快照）**：删除列/表、修改列类型、`MILVUS_COLLECTION` 变更、`DEPLOYMENT_ID` 变更、`clean`。

## 9. 需要 app 侧配合的交接项（不阻塞本轮）

以下 4 项由同事在后续迭代实现，可把「资产解耦」升级为「代码解耦」：

1. **`SCHEMA_INIT=off`**：`Service`、`DocumentStore`、`PostgresSaver.setup()` 在 Flyway 接管时跳过运行期 DDL。落地后 G4 可从 diff 改为「应用只读断言 schema 版本」。
2. **`ingest --no-collection-init`**：入库时不再调用 `MilvusVectors.ensure()`，集合生命周期完全交给 `milvus-ensure`。
3. **暴露 `SCHEMA_VERSION` 常量**（如 `app/version.py`）：供 Flyway 兼容矩阵在启动前比对，替代当前的隐式约定。
4. **`app/deployment.py` 的 `claim()` 只读化**：归属行只由 Flyway 写入，应用仅校验。

另需确认：`app/cloud.py` 要求业务账号具备 `CREATE` 权限；若第 1 项落地，可收窄为纯 DML 账号。

## 附录 B：Flyway 接管全部 SQL 的可行性与边界

> 回答一个具体问题：**不改 app、即使 app 有 DDL，能否直接用 Flyway 维护所有 SQL 并保证 app 正常运行？**
> 结论：**可以接管，但不能单独「保证」**。成立需要四个「等价」，缺一即运行时失败。

### B.1 四个等价

| # | 等价项 | 不满足时的现象 | 验证方法 |
|---|---|---|---|
| 1 | **结构等价**：按 app 的 PG 方言转换后逐字一致 | `UndefinedColumn`、类型错误、唯一索引缺失导致重复消息 | §4.5 的 G4 diff |
| 2 | **权限与属主等价**：Flyway 与应用使用同一角色，或应用角色是全部对象属主且两个 schema 有 `CREATE` | 启动第一条 `CREATE TABLE IF NOT EXISTS` 或 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 即失败 | 用应用账号执行 `db.sh migrate`，再启动应用 |
| 3 | **归属凭证行等价**：`external_deployment` 存在且 4 字段与当前环境完全一致 | `python -m app.deployment initialize` 报「数据库属于其他部署」；K8s `server.py` 启动路径不校验，但失去防护 | 比对 `metadata` 与 `DEPLOYMENT_ID/MILVUS_*` |
| 4 | **检查点版本等价**：`checkpoint_migrations` 的最大版本 = 已安装 `langgraph-checkpoint-postgres` 的 `len(MIGRATIONS)-1` | `setup()` 在应用启动时自行补迁移：能跑，但 Flyway 不再是唯一来源，新环境结构取决于启动顺序 | `python -c "from langgraph.checkpoint.postgres.base import MIGRATIONS; print(len(MIGRATIONS))"` vs `SELECT max(v)` |

当前仓库实测：`uv.lock` 锁定 `langgraph-checkpoint-postgres==3.2.1`，`MIGRATIONS` 共 10 条（0–9），baseline 已登记 0–9，`setup()` 的循环 `range(10, 10)` 为空，**今天是 no-op**。升级该依赖后必须同步 baseline。

### B.2 为什么 `IF NOT EXISTS` 救不了权限问题

- `CREATE TABLE IF NOT EXISTS`：PostgreSQL 在解析阶段就校验 schema 的 `CREATE` 权限，**不会**因为表已存在而跳过。
- `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`：仍要求表属主；列已存在只发 `NOTICE`，权限检查在前。
- `INSERT ... ON CONFLICT DO NOTHING`：仍要求 `INSERT` 权限，冲突与否不影响权限检查。
- `CREATE INDEX IF NOT EXISTS`：涉及表属主校验，最稳妥仍是同一角色。

因此：**Flyway 建好表 ≠ 应用启动能过**。角色不一致时，应用会在第一条 DDL 上直接失败。

> 现有 `FLYWAY_URL` 由 `DATABASE_URL` 生成（`scripts/dburl.py`），默认就是同一个业务账号，**当前是安全的**。这也修正了 §4.6 的建议：**在 app 改造前不要拆独立 DDL 账号**。

### B.3 长期硬约束：8 张表使用位置式 INSERT

以下语句没有列名列表，表结构列数/顺序一变就报错：

| 表 | 位置式语句 | 列数 |
|---|---|---|
| `sessions` | `INSERT INTO sessions VALUES(?,?,?,?,?,?)` | 6 |
| `workflow_runs` | `INSERT INTO workflow_runs VALUES(?,?,?,?,?,?)` | 6 |
| `tenant_message_limits` | `INSERT INTO tenant_message_limits VALUES(?,?,?)` | 3 |
| `rag_state` | `INSERT OR IGNORE INTO rag_state VALUES(1,'',0)` | 3 |
| `rag_documents` | `INSERT INTO rag_documents VALUES(?,?,?,?,?,?)` | 6 |
| `rag_revisions` | `INSERT OR IGNORE INTO rag_revisions VALUES(?,?,?,?,?,?)` | 6 |
| `rag_chunks` | `INSERT OR IGNORE INTO rag_chunks VALUES(?,?,?,?,?,?)` | 6 |
| `rag_embedding_cache` | `INSERT INTO rag_embedding_cache VALUES(?,?,?)` | 3 |

**推论**：Flyway 后续迁移的能力被锁死为：

| 允许 | 禁止 |
|---|---|
| 新建表 | 给上述 8 张表**加任何列**（列数不匹配，创建会话/入库直接 500） |
| 新建索引 | 删除列、修改列类型、调整列顺序 |
| 给 `messages` 加列（应用用具名 INSERT，安全） | 重命名表/列 |
| 给 `checkpoint_*` 加列（LangGraph 使用具名 SQL，谨慎） | 给 `external_deployment` 加列（无必要） |

这就是「维护所有 SQL」与「任意演进 schema」的区别：**前者可行，后者不可行**。

### B.4 最小验证闭环（比 diff 更强）

结构 diff 只能证明「列和索引对得上」，证明不了权限、序列、默认值行为。上线前必须跑：

```bash
# 1. 空库，用应用账号执行迁移
FLYWAY_URL="$(python3 scripts/dburl.py "$DATABASE_URL")" ./scripts/db.sh migrate

# 2. 用同一账号启动应用（不启 HTTP，只触发建表与检查点）
DATABASE_URL="$DATABASE_URL" python3 -c "from app.core import Service,Settings; s=Service(Settings()); s.close()"

# 3. 验证序列与位置式插入
psql "$DATABASE_URL" -c "INSERT INTO assistant.sessions VALUES('t','t','u','{}',0,0); DELETE FROM assistant.sessions WHERE id='t';"
psql "$DATABASE_URL" -c "SELECT nextval('assistant.messages_seq_seq');"
psql "$DATABASE_URL" -c "SELECT max(v) FROM assistant.checkpoint_migrations;"

# 4. 启动服务，发一条消息 → 重启 → 再发一条 → 查历史（覆盖 messages.seq / checkpoint 恢复）
```

CI 中把「app commit × schema version」做成矩阵，每次 app 合并都重跑；任一组合失败即阻断发布。

### B.5 一句话总结

Flyway 可以成为**唯一的 schema 变更来源**，但不能成为**唯一的 DDL 执行者**（应用启动仍会执行，只是应为 no-op）。在当前约束下，「保证 app 正常运行」= 结构等价 + 同角色 + 凭证行 + 检查点版本 + 运行时冒烟，五件事同时成立；少一件都只能算「大概率能跑」。
