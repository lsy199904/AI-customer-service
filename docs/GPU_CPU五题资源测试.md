# GPU / CPU 五题资源对照测试

## 范围

测试现有8200客服接口：5个固定问题，各自独立会话、依次发起，不并发、不调整阈值、不入库、不改变模型部署。会产生5次真实问答及历史记录。不是压力测试，不能推断50或100并发。

固定问题：

1. 注册流程是什么
2. 我想知道api如何创建
3. 如何联系人工
4. 我当前的星级是多少？
5. 如何开发票

人工、当前星级等问题可能按现有路径不调用模型，报告标为未调用，不把它视为0耗时的模型性能。问题4应核对是否正确说明无法查询个人实际星级，不应编造。

## 先部署统计代码，再测GPU

本变更基于 `v3-anonymous-iframe` 的 `3312cb0`。只新增测量和报告，不改检索、知识、图片选择或认证决策。现有流式调用明确请求usage，不缓存正文。需要将本版本代码更新至现有项目；本地交付包中的补丁可以按安装说明应用。

统计默认开启，独立文件位于 `var/cost-reports/cost-日期-进程号.jsonl`，保留30天；每个问题汇总也追加到现有请求日志。无需重建模型或重新入库，现有compose挂载项目代码，重启客服加载即可：

```bash
cd ~/ai_customer/ai_customer_v3
sh scripts/v3.sh start && sh scripts/v3.sh check
```

不需要重新安装OCR或其他依赖，也不需要重新构建镜像。测试工具仅使用Python标准库。

## 第一次：现有GPU服务

在模型服务所在服务器运行，使用当前用户已有的Docker访问权限。采集器在宿主机运行，不给客服容器挂载Docker socket，不新增公网接口；读取Docker API和cgroup数据。GPU采样需要宿主机已有 `nvidia-smi`。

```bash
cd ~/ai_customer/ai_customer_v3
python3 scripts/model_benchmark.py --mode gpu
```

默认：客服 `http://127.0.0.1:8200`；BGE容器 `ollama`；重排容器 `qwen3-reranker-4b`；客服容器 `ai_customer_v2-assistant-1`。脚本通过既有匿名身份接口获取临时凭证，不打印凭证或读取AUTH_SECRET。匿名入口必须已开启，否则会报错，不自动改认证。

先采10秒空闲基线，再依次提5题，题间隔3秒，通常数分钟，模型超时会延长。请尽量避免其他用户使用同一模型，尤其Ollama和共享GPU，以减少干扰。

终端输出报告实际路径，例如：

```text
var/model-benchmarks/gpu-20261109-时间-随机码/报告.md
```

同时保存 `results.json`、`resources.csv`（有检索调用时）、`samples.jsonl`。报告包含固定问题回答，便于人工核对。不要只看耗时而忽略业务答案。

## 第二次：维护同事切换CPU后

先确认模型服务已重新启动为CPU推理；不要只改测试标签。模型、接口、知识、检索参数、候选数和LLM应尽量保持一致。接口地址或模型名称变化时按现有流程更新客服配置并重启。

```bash
cd ~/ai_customer/ai_customer_v3
python3 scripts/model_benchmark.py --mode cpu \
  --compare-with latest
```

`latest`选择本项目最近一次GPU报告，也可换成指定报告目录。输出独立CPU报告，并额外生成 `GPU_CPU对比.md`，不覆盖GPU结果。CPU模型容器改名时显式指定：

```bash
python3 scripts/model_benchmark.py --mode cpu \
  --embedding-container 实际BGE容器名 \
  --rerank-container 实际重排容器名 \
  --compare-with latest
```

## 指标解释

| 指标 | 口径 |
|---|---|
| BGE/Reranker调用次数与耗时 | 客服实际发出的HTTP模型请求，失败也记录；含网络、服务排队及推理，不是纯内核执行时长 |
| 输入批数、重排候选数 | 对比测试工作量，防止因候选少而误判CPU更快 |
| CPU核秒 | 对应容器采样窗口内累计CPU时间的增量，包含其他请求和后台工作 |
| CPU利用率 | 核秒/采样秒数×100%；100%=占用1个逻辑核，可以超过100% |
| 平均占用核数 | CPU利用率/100；不是CPU线程数，也不是Linux内核占用 |
| 用户态/内核态CPU时间 | 原始JSON中可用时记录，不等于占用多少CPU核 |
| 内存峰值 | 采样窗口内容器内存占用峰值，包含模型常驻与可能的缓存；不是该问题新增内存 |
| 模型容器进程显存 | 将NVIDIA进程PID映射到容器后求和；共享Ollama容器仍可能含其他模型 |
| GPU利用率 | 映射到该容器进程的物理GPU整卡采样，其他模型也可能贡献，非进程独占 |
| 显存利用率 | GPU显存读写活动占比，不是已使用显存容量百分比 |
| 整卡显存、功耗、温度 | 整张物理卡共享观测，不归属于单一问题 |
| LLM输入/输出/总Token | 汇总本轮追问补齐、证据选择、图片判断和生成等真实调用；只读取服务返回的usage，不用字数估算 |
| 首字与总耗时 | 真实SSE首段文字到达及完整请求耗时 |

CPU优先读取Linux cgroup v2，默认100ms目标间隔；不可用时回退Docker统计，实际采样可能变慢。GPU查询约1秒一次，短调用可能捕捉不到负载峰值，报告必须结合原始采样看，不能认为利用率低就未使用GPU。显存值也不是精确逐请求分配。

原始调用记录含实际采样开始、结束和窗口长度。短于采样间隔、容器重启、权限不足或NVIDIA信息不可用时显示未测得，不编造成0。CPU/GPU标签由命令指定，不是自动判定的推理后端，需结合维护同事的部署配置确认。MIG/MPS等模式下PID映射可能不完整。

## 日志与计费限制

现有请求日志保留简短用量汇总，独立成本JSONL保留逐调用详情；每日按进程写文件，无问题正文或凭证。每请求报告以请求ID关联，不改变会话隔离。响应结束后才完成的后台调用会追加更新快照，脚本按最新快照汇总，不能直接逐行相加，否则会重复统计。测试最多等10秒收集更新；仍在执行或没有usage的调用标为未知，实际费用总额不能据此认为完整。

本机GPU/CPU真实数据不能在开发电脑伪造。本地自动测试使用模拟采样和响应验证逻辑；正式性能结论只认服务器实测。

共享容器窗口不能跨问题简单求和作独占CPU费用，也不能把内存或显存相加后当日资源消耗。资源成本还需要服务器月价格、运行时长和分摊方式。

## 常见问题

- 缺少cost记录：确认新代码已经加载，应用与脚本的 `var/cost-reports` 指向同一项目目录；若配置了 `COST_REPORT_DIR`、`COST_RESOURCE_SAMPLES`，脚本分别通过 `--cost-dir`、`--samples-file` 指向相同的宿主机文件。
- Docker无权限：请有Docker访问权限的维护人执行，不改socket权限、不把用户随意加入sudoers。
- 提示已有锁文件：先确认没有其他测试进程，再删除 `var/cost-reports/resource-samples.json.lock`；不要同时运行两批测试。
- 测试中断：已完成题目仍保存报告；不要据不完整报告做整体成本结论。
- 数据不足：增加问题样本或同题多轮重复，再做容量与P95分析。本版按照用户要求只执行这5题一次。
