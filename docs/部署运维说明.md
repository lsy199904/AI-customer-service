# 部署与运维

企业版 PostgreSQL + Milvus 部署、迁移与日常命令请先看 [企业升级与迁移](企业升级与迁移.md)。下文原容器/SQLite命令保留作兼容参考，企业升级后使用 enterprise.sh。

本期为一个客服进程、两个持久化SQLite数据库、一个知识源目录；模型作为独立HTTP服务提供。原生启动与Docker启动步骤见README，不要同时用两套路径维护同一套数据。SQLite不适合多实例共享，本期没有高可用方案。

整目录挂载的Linux部署方式见 [容器部署](容器部署.md)：宿主机 `~/ai_customer` 对应容器 `/ai_customer`，保留原 `var/`，无需迁移到新卷。下文named volume说明仅适用于原 `compose.yaml` 的桥接网络方式。

## 从旧版升级

在模型主机项目目录中查看本地修改：

```bash
cd ~/ai_customer
git status --short
```

如果之前只修改了 `app/core.py` 和 `.gitignore`，可先保存这些具体文件：

```bash
git stash push -m local-before-semantic-rag -- app/core.py .gitignore
git pull --ff-only origin main
```

如有其他修改，先单独保留并合并，不要直接覆盖。旧版内网HTTP校验改动不必恢复，新版有配置支持；新版 `.gitignore` 已排除 `models/`。不要盲目 `stash pop` 覆盖新实现。`.env`、数据库和模型文件不受Git跟踪。

备份旧配置和会话数据。安装依赖，保留原AUTH_SECRET与聊天模型配置，按README运行 `scripts/configure_existing_services.py` 补齐Embedding/Reranker。确认 `ANSWER_MODE=llm`，再 `check`、`ingest`，停止旧客服进程后用新版启动。旧会话继续保存；旧引用仍可通过兼容JSONL读取，新问答只使用新索引。刷新浏览器获取新版窗口脚本。

## 模型服务与迁移

在当前主机最省事的是复用已运行的服务。`models/ollama/models` 和 `models/reranker` 是用户复制的权重，保存它们不会让模型自动运行；本次代码不额外启动GPU模型，避免占用已有推理显存。

迁移到其他主机时，带上代码、源目录、两个数据库、受控传输的.env；模型可以继续访问现有服务，或在新主机单独部署Ollama/vLLM并挂载这些权重。重新部署模型需要另外核对显存、服务版本、GPU驱动及接口参数。不要把9GB模型权重提交Git。更换Embedding地址/权重后按说明重建并验收；Reranker、聊天模型只需调整地址和认证及重启。

Docker内127.0.0.1不是宿主机，详情见README的复用网络配置。重排容器IP可能随重建改变，原生部署可重新运行配置辅助脚本；Docker同网络使用容器DNS更便于维护。

## 端口与超时

默认仅监听宿主机127.0.0.1:8000，公网通过HTTPS代理。Embedding与Reranker各最多等待60秒，聊天模型45秒，代理读取超时模板设200秒。外部网关有自己的超时也需对应配置。不要用调大超时掩盖模型服务拥塞。

CORS_ORIGINS填写真实业务页面来源；已有登录Cookie不会自动成为助手凭证，需要业务后端签发。模板禁止公网访问联调页。`/health`仅证明进程存活，不证明索引和模型可用；用 `check` 加真实问答检查业务可用性。

## 备份

原生部署：

```bash
python manage.py backup
```

备份分别为 `backups/assistant-时间.sqlite3` 和对应 `-knowledge.sqlite3`，使用SQLite备份API并做完整性校验，不覆盖同名文件。后者包含向量、历史修订及原文快照。

Docker部署，在容器里输出到持久化目录后导出，例如：

```bash
# 固定示例名仅使用一次，下次换名，避免覆盖
# 使用叠加配置时，每条docker compose命令也加相同的两个-f参数
docker compose exec assistant python manage.py backup --output /srv/assistant/var/backup-001.sqlite3
mkdir -p backups
docker compose cp assistant:/srv/assistant/var/backup-001.sqlite3 backups/backup-001.sqlite3
docker compose cp assistant:/srv/assistant/var/backup-001-knowledge.sqlite3 backups/backup-001-knowledge.sqlite3
```

另外备份 `knowledge_sources/`、`.env`、部署配置。源文件和密钥不包含在数据库导出里。备份包含客户对话和知识原文，按企业策略限制访问。历史修订不会自动清除，需监测磁盘空间。

## 恢复

先为当前数据做备份，停止客服与所有入库任务；校验两份待恢复文件的 `PRAGMA integrity_check` 均为 `ok`。用经校验的会话备份替换DATABASE_PATH，用知识备份替换RAG_INDEX_PATH，清理停止后的同名 `-wal`/`-shm` 临时文件，恢复对应源目录及.env，然后启动并验证历史、索引、问答和文档下载。不要覆盖仍在运行的数据库。

Docker需在挂载同一卷的临时维护容器中操作，恢复文件属主设10001:10001。不要删除数据卷，也不要变更Compose项目名后误用新卷。这里未提供自动覆盖脚本，运维应在测试环境先验证恢复流程；本机没有Docker，容器步骤尚未实测。

## 故障排查

|现象|排查|
|---|---|
|AUTH_SECRET错误|保留原随机值，至少32字节；不要将其交给浏览器|
|提示设置RERANK_URL|旧.env缺少新参数，运行配置辅助脚本或按模板补齐|
|知识数为0|先执行ingest，检查是否用错索引路径或容器卷|
|retrieval_unavailable|检查Embedding/Reranker可达性、重排密钥、向量维度与索引配置；不会自动改用词法检索|
|model_unavailable|检查/v1基础地址、模型名、密钥、超时与模型JSON输出兼容性|
|配置变更要求重建|更换Embedding配置后执行ingest --rebuild|
|大量误命中或漏检|检查清洗文档、真实问题的召回与拒答，再校准语义门槛；评分不是概率|
|新内容未生效|确认覆盖相同路径、已成功入库、文档未停用；检查updated/unchanged结果|
|停用后仍能下载旧文档|为保留历史来源的预期行为；停用不会销毁快照|
|短期凭证无效|重新签发，检查有效期及签名密钥一致性|
|改.env不生效|系统环境变量优先；重启原生服务或重新创建容器|
|独立HTML表现未变|它是离线旧数据原型，真实Word RAG请使用/widget/demo|

请求日志不记录凭证、问题正文和查询参数。当前没有完整监控面板、自动会话清理或数据库应用层加密。正式上线仍需完成真实模型质量、登录接入、容量、监控与备份恢复验收。
