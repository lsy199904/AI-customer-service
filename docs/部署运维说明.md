# 部署与运维

## 本期部署形态

一个客服服务实例，一份持久化SQLite数据库，一份本地只读知识文件。悬浮组件由同一服务提供，无需独立部署前端站点。主入口见项目README。当前无自动扩缩容或多实例会话锁方案，不能直接横向复制实例共享SQLite。

## 端口、TLS与现有登录

原生默认127.0.0.1:8000；Docker也只映射本机端口，避免绕过现有网关。公网使用HTTPS反向代理，Nginx模板位于deploy目录，替换域名和证书路径后验证语法再部署。模型读取超时45秒，代理超时65秒。联调页不会被模板开放到公网。

业务页面需配置精确CORS_ORIGINS；页面与服务同源时无需额外跨域配置。当前浏览器CSP策略需允许widget脚本、接口连接及组件样式。已有控制台的登录Cookie不会自动变成助手身份，须由可信控制台后端验证登录后签发短期凭证。SSO和模型配置缺失不会被静态原型掩盖。

## Docker数据库一致性备份

先在容器内调用SQLite备份API。以下固定使用新文件名；已有同名备份请改名，防止误覆盖：

```bash
docker compose exec assistant python -c "from pathlib import Path; import sqlite3; p=Path('/srv/assistant/var/backup.sqlite3'); assert not p.exists(), 'backup exists'; s=sqlite3.connect('/srv/assistant/var/assistant.db'); d=sqlite3.connect(str(p)); s.backup(d); print(d.execute('PRAGMA integrity_check').fetchone()[0]); d.close(); s.close()"
```

看到`ok`后，在宿主机创建backups目录，再导出：

```bash
mkdir -p backups
docker compose cp assistant:/srv/assistant/var/backup.sqlite3 backups/assistant-backup.sqlite3
```

文件含业务对话，请限制访问并按企业备份策略保存。示例不会删除容器内备份；下次备份须使用新文件名，或在确认已妥善导出后按运维流程清理旧备份。

## 恢复

先保留当前数据库的一致性备份，停止服务。原生方式将经校验的备份文件放回DATABASE_PATH对应位置后启动。不要用备份覆盖仍在运行的数据库。

Docker方式可用临时容器挂载同一个卷完成恢复：

1. 执行 `docker compose stop assistant`。
2. 在本机确认待恢复文件的PRAGMA integrity_check结果为ok。
3. 使用 `docker compose run --rm --no-deps --user 0 -v "$PWD/backups:/restore:ro" assistant python -c "from pathlib import Path; import sqlite3; s=sqlite3.connect('file:/restore/assistant-backup.sqlite3?mode=ro', uri=True); assert s.execute('PRAGMA integrity_check').fetchone()[0]=='ok'; d=Path('/srv/assistant/var'); [p.unlink() for p in d.glob('assistant.db*') if p.name in ('assistant.db','assistant.db-wal','assistant.db-shm')]; t=sqlite3.connect(str(d/'assistant.db')); s.backup(t); t.close(); s.close()"`。
4. 恢复过程以root运行,需把恢复文件所属用户改回10001：`docker compose run --rm --no-deps --user 0 assistant chown 10001:10001 /srv/assistant/var/assistant.db`。
5. 执行 `docker compose up -d assistant`，验证历史读取与健康检查。

第3步会替换当前数据库，务必先完成第1、2步和当前数据备份；恢复是运维操作，不是日常启动步骤。本环境无Docker，以上容器运维示例尚未实测，部署人员应在测试环境验证备份恢复后上线。

## 常见故障

|现象|排查|
|---|---|
|没有.env|执行python3 manage.py init,再编辑配置|
|AUTH_SECRET校验失败|使用至少32字节随机值,不能留空|
|改.env后未生效|重启进程;系统环境变量优先,检查旧环境变量;容器需force-recreate|
|回答显示原文摘录|ANSWER_MODE仍为extractive;设llm并配置模型后重启|
|model_unavailable|检查基础地址是否重复了chat/completions、model ID、密钥权限、出口网络和JSON输出兼容性|
|窗口提示登录凭证无效|短期凭证过期、签名密钥不一致或登录系统未接入;重新签发测试凭证|
|请求来源未授权|CORS_ORIGINS填实际页面来源,包括协议和端口,不填页面路径|
|服务健康但没有AI回答|health只验证进程,不验证外部模型;需要真实问答验收|
|重启后历史消失|检查数据库路径或Docker项目名变化导致使用了新卷,不要执行down -v|
|独立HTML刷新丢历史|符合原型设计;需要数据库持久化请使用真实联调页|
|点击原文链接不可用|SOURCE_BASE_URL未配置或原PDF尚未部署;条目来源查看不依赖原PDF|

## 升级、日志与保留期

升级前备份数据和配置,保留旧代码版本。修改Python代码后重启,容器方式重新构建。知识数据读取后缓存在内存,更新JSONL也需要重启。

标准请求日志不记录请求正文、凭证和用户问题。模型失败当前仅向客户端返回统一兜底,未提供完整上游诊断面板或监控系统;需要由实际运维环境收集进程日志与可用性指标。SQLite对话数据明文保存,未启用自动清理策略;保留期、备份访问与磁盘保护由企业部署要求确定。

## 从旧版更新本次修正

在~/ai_customer执行git pull之前先查看git status。如果此前按说明手改过app/core.py,可以先执行`git stash push -m local-core-before-conversation-fix -- app/core.py`保存该文件的本地变更,再`git pull --ff-only origin main`。新版本已提供内网HTTP配置,不需要恢复旧的HTTPS校验修改;其他自定义修改应检查后手动合并。`.env`不受Git跟踪,不会被上传或覆盖。

内网模型示例:

```dotenv
ANSWER_MODE=llm
MODEL_BASE_URL=http://10.180.158.23:18080/v1
MODEL_HTTP_ORIGINS=http://10.180.158.23:18080
MODEL_API_KEY=not-empty
MODEL_NAME=Qwen/Qwen3-32B
RETRIEVAL_MIN_SIMILARITY=0.14
SUPPORT_QR_URL=
```

保留已有AUTH_SECRET。更新配置后检查并重启服务,浏览器刷新以获取新widget.js。相似度是词法相关性指标,不是概率或Embedding语义评分;极端降低阈值会增加误匹配。日志/接口保留模式与评分供开发排查,客户窗口隐藏技术模式提示。
