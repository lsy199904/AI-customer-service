# 当前 Linux 主机的容器部署

此方式把宿主机整个项目目录挂载为容器的 `/ai_customer`。按当前用户的UID/GID运行，继续使用项目内原有配置、文档及数据库，不自动创建新的数据卷。依赖由Dockerfile在镜像构建阶段安装，无需在宿主机创建虚拟环境，也无需进入运行容器手动pip安装。

```text
宿主机 /home/sylvanli/ai_customer  →  容器 /ai_customer
      app/                           /ai_customer/app/
      knowledge_sources/             /ai_customer/knowledge_sources/
      var/                           /ai_customer/var/
      models/                        /ai_customer/models/
```

模型目录只挂载，不复制进镜像，不会自动加载模型。客服仍调用当前主机已有的Ollama、Reranker和Qwen接口。此配置使用Linux宿主机网络，因此Ollama的 `http://127.0.0.1:11434/api/embed` 可继续使用；不需要重新配置Ollama的监听地址。重排沿用可达的容器IP，IP改变后重新运行配置辅助脚本并重新创建客服容器。

## 拉取和配置

```bash
cd ~/ai_customer
git pull --ff-only origin main
python3 scripts/configure_existing_services.py
```

辅助脚本只用宿主机Python标准库与Docker命令读取模型配置，不安装宿主机Python依赖。保留已有AUTH_SECRET，确认实际.env中的 `ANSWER_MODE=llm` 及Qwen模型地址、名称正确。密钥仅保存在本机.env。宿主机需要Docker Engine及Compose插件；使用原来能访问Docker的普通用户运行下列脚本，不必切换root。

如果原来的Python客服仍占用8000端口，先在原终端Ctrl+C停止该客服进程。不要停止共享的模型服务。整个部署过程保留 `var/` 和 `models/`。

## 构建并启动

```bash
# 构建时在镜像内自动安装requirements.txt，再后台启动
sh scripts/docker-host.sh up --build -d

# 确认运行状态和启动日志
sh scripts/docker-host.sh ps
sh scripts/docker-host.sh logs --tail=100 assistant

# 在容器中校验配置并首次入库
sh scripts/docker-host.sh exec assistant python manage.py check
sh scripts/docker-host.sh exec assistant python manage.py ingest
sh scripts/docker-host.sh exec assistant python manage.py check
```

首次入库前知识数量为0是预期状态，入库成功后首份Word通常产生18个片段。若已有不同Embedding配置的索引提示必须重建，确认模型设置后执行 `ingest --rebuild`，不要删除数据库。启动失败时先看日志；不要在失败容器里反复执行入库。

`ps`和健康检查确认进程运行；真实模型可达性和回答质量仍需联调。容器默认在宿主机127.0.0.1监听.env中的PORT（默认8000）。通过原有SSH隧道或HTTPS代理访问 `/widget/demo`，不是直接把容器内地址填到浏览器。

测试凭证：

```bash
sh scripts/docker-host.sh exec assistant python manage.py token --tenant demo-company --user demo-user
```

进入容器终端：

```bash
sh scripts/docker-host.sh exec assistant sh
# 工作目录已经是 /ai_customer
```

## 日常维护

新增或修改宿主机 `knowledge_sources/` 文件后，容器立即能看到文件；再执行入库才能更新问答：

```bash
sh scripts/docker-host.sh exec assistant python manage.py ingest
```

修改Python代码后重启客服进程；修改requirements.txt后重新构建镜像；修改.env后重新创建容器，使新环境变量生效：

```bash
# 仅改代码
sh scripts/docker-host.sh restart assistant

# 改依赖
sh scripts/docker-host.sh up --build -d

# 改.env
sh scripts/docker-host.sh up -d --force-recreate assistant
```

运行中一致性备份会话和知识库：

```bash
sh scripts/docker-host.sh exec assistant python manage.py backup
```

文件保存在宿主机 `~/ai_customer/backups/`。源文档、.env和模型文件另外按需备份。停止或移除客服容器不会删除宿主机数据：

```bash
sh scripts/docker-host.sh down
```

本文件对应独立 `compose.host.yaml`，不要和原桥接网络Compose文件混用启动同一个服务。整目录挂载意味着容器中对项目文件的写入也会反映到宿主机。当前本机没有Docker，已验证脚本参数、UID/GID、配置保留与密钥不打印；实际镜像构建和目标主机模型连接待服务器验证。
