# SmartTITU匿名智能客服部署说明

版本：release-anonymous-20261111

编制日期：2026年11月11日

适用范围：在新的Linux主机独立部署匿名客服服务，并以JavaScript脚本嵌入平台页面。

## 1 交付范围与部署边界

本版本以 `deploy-smart-bot-20261110-151538` 分支提交 `5596c012d3dfa30c8d50f160654c70c966843789` 为基础建立独立发布分支。原部署分支和原服务不被自动修改。

本版保留匿名身份、历史会话、流式回答、知识引用、配图、人工联系方式和请求排障日志；移除旧Demo页面、Demo凭证签发接口及其专用资源。正式前端接入使用 `/smart-bot/iframe-anonymous.js`，独立接入检查页使用 `/smart-bot/widget/anonymous-demo`。原 `/widget/demo`、`/widget/demo-auth` 等入口返回404，旧Demo身份不能访问本版业务接口。

统一Compose包含以下服务：

| 服务 | 功能 | 数据保存位置 |
|---|---|---|
| assistant | 浮窗资源、接口、流程编排、检索与回答 | 项目`var/`及PostgreSQL |
| postgres | 会话、消息、工作流检查点、知识文本、版本与向量副本 | `postgres-data`命名卷 |
| etcd | Milvus元数据协调 | `etcd-data`命名卷 |
| minio | Milvus对象存储 | `minio-data`命名卷 |
| milvus | 在线向量索引与检索 | `milvus-data`及上述关联存储 |

本版不在Compose内启动回答模型、Embedding模型或重排模型。部署方须预先准备三个可用模型接口及访问权限。模型由CPU还是GPU承载不改变客服的接口协议要求；更换Embedding模型或处理方式需要重建索引。

正式接入还需要可用域名、HTTPS证书和反向代理。仓库提供Nginx示例，不自动安装Nginx或签发证书。单机方案不提供跨主机高可用。

## 2 主机与网络准备

### 2.1 基本条件

- Linux主机，支持Docker Engine与Compose V2，Compose需支持`up --wait`。
- 宿主机具备Python 3.10或以上，用于配置和资源打包；应用镜像使用Python 3.12。
- 部署账号可以执行Docker命令，并对项目目录具有读写权限。
- Milvus 2.6独立实例官方建议至少4核CPU、16 GiB内存，具体容量随数据量变化；本方案还运行应用、PostgreSQL等服务，应预留额外资源。可先以8 vCPU、32 GiB内存和100 GiB可用SSD作为小规模整套联调的资源预算示例，不包含模型资源，不作为最低配置或吞吐承诺；以目标负载测试确定最终配置。CPU需支持Milvus要求的SIMD指令集，磁盘优先使用本地SSD。参考：[Milvus 2.6部署要求](https://milvus.io/docs/v2.6.x/prerequisite-docker.md)。
- 联网主机可拉取固定版本基础镜像与Python依赖；离线主机需事先导入全部镜像及已构建的应用镜像。

### 2.2 端口与服务连接

| 端口 | 默认用途 | 暴露范围 |
|---|---|---|
| 443 | HTTPS接入 | 按平台网络策略开放 |
| 80 | 跳转HTTPS | 可按公司网关规范处理 |
| 8200 | 客服应用 | 默认仅监听`127.0.0.1`，由网关代理 |
| 55432 | PostgreSQL | 仅宿主机回环地址 |
| 19530 | Milvus | 仅宿主机回环地址 |
| 2379、9000等 | etcd、MinIO内部通信 | Compose网络内部，不映射宿主机 |

应用使用Linux宿主机网络连接本机数据库、Milvus及配置的模型接口。网关若位于另一台主机，应将`V3_HOST`设为适合的监听地址，并通过防火墙仅允许网关访问应用端口；不能继续代理网关自己的`127.0.0.1`。

同一主机并行保留旧服务时，新版的应用端口、PostgreSQL端口、Milvus端口和`COMPOSE_PROJECT_NAME`必须独立。`init`会依据本版端口生成数据库与Milvus连接串。旧服务可能占用19530等端口，启动前必须检查；不要通过删除旧容器或数据卷解决冲突。

### 2.3 镜像准备

默认版本沿用已选定部署基线，不表示自动采用最新版本：

```text
postgres:16.10-bookworm
quay.io/coreos/etcd:v3.5.18
minio/minio:RELEASE.2024-05-28T17-19-04Z
milvusdb/milvus:v2.6.4
smarttitu-assistant:release-20261111（本项目构建）
```

可在`.env`中将镜像变量替换为公司镜像仓库地址，但应使用内容一致且验证过的版本。应用构建基础镜像为`python:3.12-slim`；联网构建还需访问Debian包源及Python包源。受限环境可由构建机完成构建并推送公司镜像仓库，新主机导入应用与四个基础设施镜像后跳过build。镜像不属于普通项目目录，复制源代码不会复制本机Docker镜像。

## 3 获取版本及准备知识资源

### 3.1 获取发布代码

从公司GitLab获取本发布分支或公司约定的发布标签，放入新的独立目录；不覆盖现有生产目录。初始化时不直接复制旧服务`.env`，避免把新主机指向原数据库或原Milvus。

### 3.2 源文件与入库数据的区别

运行需要完整保留：

```text
knowledge_sources/      Word、PDF、Markdown、TXT源文档
data/media.json         配图ID、标题和资源映射
app/static/media/        静态流程图和界面图片
var/pdf_media/           PDF入库提取图片及清洗登记（存在时一并迁移）
```

`knowledge/`是旧整理资料，不再交付。`data/knowledge.jsonl`仍保留用于代码兼容，不代替语义入库。仅复制Word、图片和登记文件不会自动生成新数据库中的检索索引；新库仍需执行ingest。

发布分支自带的知识资源来自Git已提交内容。旧服务器未提交的`data/media.json`、Word及本地生成图片不会自动出现在新分支。上线前应以旧服务器已确认的正式知识资源为准，核对并同步；不得以本发布分支的提交日期代替知识内容的版本确认。

### 3.3 从旧服务器导出当前资源

在仍运行旧版本的项目目录执行（不停止旧服务）：

```bash
cd ~/ai_customer/ai_customer_v3
python3 scripts/knowledge_bundle.py pack \
  --output /tmp/smarttitu-current-knowledge.tar.gz
```

该资源包包含源文档、图片登记、静态图片和标准PDF图片目录，不包含`.env`、模型权重和聊天数据库。通过公司授权渠道复制资源包至新主机。

新发布目录必须具备本版代码，但其资源可能与旧服务器不同。先备份本版资源，再移开四个待替换位置，使目标资源路径为空；保留`app/static/`中其他JS和CSS。所有操作应在新发布目录执行，不能在旧生产目录执行：

```bash
mkdir -p backups/resources-before-import
tar -czf backups/resources-before-import/resources.tar.gz \
  knowledge_sources data/media.json app/static/media
# 若var/pdf_media已存在，另行备份。
mv knowledge_sources backups/resources-before-import/knowledge_sources
mv data/media.json backups/resources-before-import/media.json
mv app/static/media backups/resources-before-import/media
if [ -d var/pdf_media ]; then
  mv var/pdf_media backups/resources-before-import/pdf_media
fi
python3 scripts/knowledge_bundle.py restore \
  --archive /实际路径/smarttitu-current-knowledge.tar.gz
```

恢复工具会校验清单和文件哈希，并拒绝覆盖不同内容。导入后执行`git status --short`，审核需要纳入公司仓库的源文档和资源变更。不要提交资源包、运行日志或私密备份。

## 4 配置初始化

### 4.1 生成本机配置

在新发布目录执行：

```bash
sh scripts/v3.sh init
```

该命令从`.env.example`建立`.env`，生成随机身份密钥、运维密钥、PostgreSQL应用账号密码、MinIO和Milvus凭证，并生成本机`deploy/generated/milvus-user.yaml`。已有的非空密钥不会轮换。`.env`为当前用户可读写文件，生成配置不进入Git。

如果需要更换默认端口，应先复制`.env.example`为`.env`、修改端口，再执行init。配置已有连接串与新端口不一致时初始化会拒绝继续，避免误连接其他环境。

`init`不启动服务，不自动验证模型可用性。投入使用后不要通过重新填写密码来“修改数据库账号”：PostgreSQL初始化脚本只在全新数据卷执行，已有账号需使用数据库管理流程变更。

### 4.2 必填配置

编辑`.env`，至少核对下表；完整注释见模板。

| 参数 | 设置要求 |
|---|---|
| `MODEL_BASE_URL`、`MODEL_NAME`、`MODEL_API_KEY` | 正文生成模型的基础URL、对外模型名及密钥；基础URL一般以`/v1`结尾 |
| `EMBEDDING_PROVIDER` | 当前模板为OpenAI兼容协议`openai` |
| `EMBEDDING_URL`、`EMBEDDING_MODEL`、`EMBEDDING_API_KEY` | 完整向量化接口、模型名、密钥 |
| `RERANK_URL`、`RERANK_MODEL`、`RERANK_API_KEY` | 完整重排接口、模型名、密钥 |
| `MODEL_HTTP_ORIGINS` | 使用HTTP模型服务时，明确允许协议、主机和端口；多个来源用逗号分隔 |
| `FRAME_ORIGINS` | 实际平台页面origin，含协议、域名及必要端口，不含路径，不填通配符 |
| `ANONYMOUS_COOKIE_SECURE` | 正式HTTPS接入设`true`；纯HTTP临时联调设`false` |
| `V3_HOST`、`V3_PORT` | 应用监听地址和端口；同机网关默认回环地址8200 |
| `COMPOSE_PROJECT_NAME` | 数据卷及容器命名空间；新旧环境分开，使用后保持稳定 |

模板中的127.0.0.1只是示例模型地址。若模型位于其他服务器，必须替换为新主机能访问的真实地址，并同步HTTP来源白名单。密钥不可放入前端脚本或文档。若模型服务无鉴权，聊天客户端仍要求非空MODEL_API_KEY，可在确认服务协议后使用约定占位值；不要将占位值误认为真实鉴权。

### 4.3 默认策略

| 项目 | 默认值及含义 |
|---|---|
| 历史消息保留 | 最近7天；后台定期清理过期消息、会话和检查点 |
| 匿名身份Cookie | 30天；成功认证时续期，浏览器策略可能提前清除或阻止存储 |
| 接口Token | 1小时；浮窗自动续取，续取沿用有效匿名身份 |
| 提问额度 | 匿名默认企业全部用户共用滚动60秒20次；不是每个用户20次 |
| 上下文轮数 | 最多20轮；不是页面历史总条数 |
| 空闲阈值 | 1800秒；空闲后开启新的上下文片段，历史仍受7天规则控制 |
| 检索预算 | 在线Embedding、召回和重排共享15秒；回答生成另计 |
| 语义门槛、重排门槛 | 模板均为0.60；实际业务问法需回归验证，不代表回答准确率 |
| 普通日志 | 30天，按日期和大小轮转 |
| 完整正文排障 | 默认关闭；临时开启后按3天保留 |

生产提问额度应通过目标模型容量测试确定。提高额度不是扩大硬件或模型吞吐能力。前端并发多时还可能触发同会话忙、服务并发限制或模型服务自身限制。

## 5 首次部署

### 5.1 构建应用

确认知识资源已导入，模型配置已填写：

```bash
sh scripts/v3.sh build
```

应用将项目目录挂载到容器`/ai_customer`。运行期间禁止在项目目录执行破坏性清理；`var/`、源文档和图片都是有效运行资源。

如使用离线镜像，新主机先执行`docker load -i 镜像包.tar`；镜像标签与.env一致时可跳过build。实际镜像包由联网构建环境准备，不包含在源代码ZIP中。

### 5.2 启动基础设施

```bash
sh scripts/v3.sh infrastructure
sh scripts/v3.sh ps
```

此步骤只启动PostgreSQL、etcd、MinIO和Milvus，并等待健康检查。不会启动旧目录里的服务，也不会初始化任何模型服务。失败时先查看对应服务日志，不执行`down -v`。

首次入库前可以检查基础配置与模型服务：

```bash
sh scripts/v3.sh check
```

check为空知识库时可能报告知识尚未准备；它不替代首次ingest或模型实测。

### 5.3 入库

```bash
sh scripts/v3.sh ingest
sh scripts/v3.sh documents
```

ingest使用一次性应用容器执行，不依赖客服进程已就绪，因此新数据库无需先启动一个无法通过ready检查的应用容器。该过程解析知识源、生成Embedding、写入PostgreSQL并同步Milvus；PDF图片提取可能在首次处理时耗时较长。

Embedding接口故障会导致入库或在线检索失败。先确认模型接口连通及模型名，不通过降低相似度门槛解决连接故障。

只修改前端文案、样式或接入路径，无需入库。修改文档内容执行ingest；Embedding版本或切分方式变化执行：

```bash
sh scripts/v3.sh ingest --rebuild
```

同一份内容不应以两个文件名重复保留在入库目录。需要停用旧文档时使用`manage.py deactivate`显式管理活动状态，不依赖删除源文件立即清除数据库内容。

### 5.4 启动并检查

```bash
sh scripts/v3.sh start
sh scripts/v3.sh doctor
curl -fsS http://127.0.0.1:8200/smart-bot/health
curl -fsS http://127.0.0.1:8200/smart-bot/ready
```

start仅创建或重建应用容器，不清空数据卷。doctor --models实际检查数据库、知识、向量检索、Embedding、重排及回答模型。health仅表示HTTP服务存活；ready检查数据连接和索引，不保证每次模型请求成功。两者均不能替代业务问答验证。

应用端口变更后同步修改检查命令、网关和接入脚本URL。`ps`用于确认容器健康状态，`logs`用于查看应用启动输出。

## 6 HTTPS网关与平台接入

### 6.1 网关

参考`deploy/nginx.conf.example`配置真实域名、证书和应用地址。核心要求：

- 对外所有客服请求使用`/smart-bot`前缀，代理保留此前缀。
- SSE关闭代理缓冲和缓存，读取超时不短于模型处理预算。
- 平台为HTTPS时，脚本和iframe也使用HTTPS，避免混合内容被浏览器拦截。
- 默认不对公网开放PostgreSQL、Milvus、etcd、MinIO或运维指标。

代理示例的`proxy_pass http://127.0.0.1:8200;`没有尾部斜杠。应用内部会规范化前缀，日志可能显示`/v1/...`；完整外部请求URL应在浏览器Network或网关访问日志中确认。

### 6.2 接入代码

平台前端在页面加载：

```html
<script src="https://assistant.example.com/smart-bot/iframe-anonymous.js"></script>
```

该脚本创建独立样式的悬浮入口和iframe，自动获取匿名Token、创建和读取会话并发起SSE问答。平台不需要填写账号密码、固定API密钥或手工调用每个接口。

| 外部路径 | 用途 |
|---|---|
| `GET /smart-bot/iframe-anonymous.js` | 平台接入脚本 |
| `GET /smart-bot/chatbot/anonymous` | iframe内聊天页面 |
| `POST /smart-bot/widget/anonymous-auth` | 获取或续取匿名凭证 |
| `GET /smart-bot/v1/bootstrap` | 客服初始化数据 |
| `GET/POST /smart-bot/v1/sessions` | 获取或新建会话 |
| `GET /smart-bot/v1/sessions/{sid}/messages` | 当前用户的会话历史 |
| `POST /smart-bot/v1/sessions/{sid}/messages/stream` | 流式发送问题与回答 |
| `DELETE /smart-bot/v1/sessions/{sid}` | 删除当前用户拥有的会话 |
| `GET /smart-bot/media/...` | 图片资源 |
| `GET /smart-bot/widget/anonymous-demo` | 与正式脚本一致的接入检查页 |

业务接口携带`Authorization: Bearer <token>`，由浮窗内部自动处理。内部签名密钥AUTH_SECRET只保留在后端。匿名认证接口公开发放访客凭证，不执行真实账号验证；来源白名单不等于真实身份认证。

### 6.3 身份和会话边界

后端签发默认企业`__smarttitu_anonymous__`和随机`anon-...`用户ID。接口验证签名、有效期，并按企业＋用户核对会话归属。不同匿名用户不能仅凭会话ID访问他人消息。每个会话独立保存上下文。

同一浏览器有效Cookie通常沿用身份；换浏览器、清除Cookie或浏览器限制第三方Cookie后，历史连续性不保证。支持分区Cookie的浏览器可能按宿主站点隔离身份。共享电脑同一浏览器配置无法自动识别换人；匿名模式不提供跨设备真实账号同步。7天是消息保存策略，不是访客历史必然可恢复的承诺。

若后续接入真实平台账号，应由可信后端提供身份映射和签名机制，不能直接信任浏览器任意传入的user_id。

## 7 日志与数据管理

日志写入当前主机项目目录，不自动汇入PostgreSQL：

```text
var/logs/app-日期-进程.jsonl
var/logs/conversations/年-月/tenant-摘要/user-摘要/session-摘要.jsonl
```

普通运行日志记录接口、状态、耗时和异常分类；会话日志按月、企业、用户、会话归档。LOG_DEBUG_CONTENT和LOG_TRACE_DETAIL控制正文及详细节点信息。日志保留期独立于网页消息保留期；开启正文排障时限制读取权限并及时关闭。Token用量与模型调用计时能力保留，单机资源采集压测脚本不在本交付范围。

PostgreSQL的`assistant.sessions`保存会话，`assistant.messages`保存消息与响应，`assistant.workflow_runs`及检查点表保存流程状态；`knowledge` schema保存知识数据。数据库总大小不等于聊天表大小。

`var/pdf_media/`包含可被回答引用的图片，不得作为普通临时日志清空。Docker命名卷也不属于项目源代码目录，完整迁移不能只复制源码。

## 8 备份恢复与版本切换

### 8.1 备份

```bash
sh scripts/v3.sh backup
```

备份期间应用短暂停止接收请求，完成后恢复原运行状态。输出位于`backups/snapshot-时间/`：

- `database.dump`：数据库逻辑备份，包括会话、检查点和知识数据；
- `knowledge.tar.gz`：源文档、登记文件和图片资源；
- `environment.private`：真实环境配置，含密钥，仅限授权保管。

此备份不逐卷复制Milvus、MinIO或etcd，恢复时使用PostgreSQL保存的知识向量重建Milvus索引。备份与代码分开加密保存，并定期在空环境演练。备份命令失败时检查输出目录，不把未完成快照当成可恢复备份。

### 8.2 恢复至新的空环境

1. 准备匹配代码、完整资源及基础镜像，应用保持停止。
2. 从私密备份恢复环境参数；保留AUTH_SECRET及数据库账号，按新主机调整模型、域名、端口。若端口变更，同步修正DATABASE_URL、MILVUS_URI；初始化工具会拒绝矛盾配置。
3. 执行init生成Milvus配置，再启动基础设施。
4. 导入知识资源。目标已有不同文件时先备份移开，再用restore-bundle导入，方法见第3节。
5. 将数据库备份恢复至没有assistant、knowledge业务表的新库：

```bash
sh scripts/v3.sh restore-db /实际路径/database.dump
sh scripts/v3.sh sync-vectors
sh scripts/v3.sh doctor
sh scripts/v3.sh start
```

恢复脚本不自动删除已有表，不使用`--clean`。若目标库已初始化业务表而恢复冲突，应另建干净环境核对，不强行覆盖。新环境只需相同知识、不保留历史时，不导入database.dump，按首次部署流程重新ingest即可。

数据库恢复不保证原浏览器能找到旧匿名历史；访问域名、Cookie范围和签名密钥变化都可能造成身份不连续。

### 8.3 升级与回退

代码更新前先做备份并记录分支、提交、镜像版本和配置。仅前端或Python源码变化可按需要重建应用容器；依赖或Dockerfile变化必须重新构建镜像。知识变更执行入库，未变更不重复执行重建。

旧目录和旧服务作为回退基线保留。并行验证新版时使用独立项目名、数据库卷和端口，确认后由网关切流。回退时切回旧网关目标；不要让新旧版本同时连接正在迁移的同一业务库，也不通过删除命名卷回退。
