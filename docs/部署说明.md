# SmartTITU 外部服务部署说明

版本分支：`deploy-external-api-20261116`。本入口适用于Linux Docker Compose V2，模型、PostgreSQL和Milvus均已由部署方提供。只创建一个App容器，不启动数据库、etcd、MinIO，不迁移研发历史数据。

## 1 部署方准备

| 项目 | 必须提供 |
|---|---|
| 主机 | Linux、Docker Engine、Compose V2（支持`up --wait`）、宿主机Python 3.10以上；Docker权限和项目目录读写权限 |
| 应用资源 | 本分支完整代码、`knowledge_sources/`、`data/media.json`、`app/static/media/`；`var/pdf_media/`可通过首次入库生成 |
| PostgreSQL | 16.x，已创建的独立业务数据库、连接串、账号密码；账号拥有业务库CREATE权限及所建schema、表、索引的所有权，能创建LangGraph检查点 |
| Milvus | 兼容2.6及PyMilvus 2.6.17的Endpoint、Token、数据库名；对应库的集合列表、创建、读取、写入、建索引和flush权限 |
| LLM | OpenAI兼容Chat Completions接口基础URL（通常以`/v1`结尾）、API Key、模型ID |
| Embedding | OpenAI兼容接口完整URL、API Key、模型ID；需返回`data[index,embedding]` |
| Rerank | 完整URL、API Key、模型ID；需返回`results[index,relevance_score]`且支持全部候选评分 |
| 网络及访问 | App到数据库和三个模型接口连通；正式访问域名、HTTPS网关及父页面origin；SSE关闭缓冲 |

Milvus若自建，由基础设施人员维护etcd、MinIO和持久化数据；若托管，则由供应商维护。App不配置这两个服务。只写“Milvus 2.6”不足以确认托管接口兼容，尤其需要确认索引类型和flush支持。

应用目录需要持久化。`var/pdf_media/`不是临时日志，不可清空。当前Compose将本项目挂到`/ai_customer`；采用宿主机网络，数据库地址对容器来说就是宿主机可访问的地址。该Compose不能直接部署为Kubernetes Pod，Pod部署需另行提供Deployment、Secret、PVC和网关配置。

## 2 全新生产部署

### 2.1 获取代码并准备配置

```bash
git clone --branch deploy-external-api-20261116 --single-branch \
  ssh://git@ssh.github.com:443/lsy199904/AI-customer-service.git \
  ai_customer_external
cd ai_customer_external
sh scripts/external.sh init
```

公司内网可将仓库地址替换为公司GitLab对应分支。不要覆盖旧目录，不要直接复制旧.env。

编辑生成的`.env`，逐项填写。密钥不能提交Git，不执行`source .env`。

| 参数 | 填写方式 |
|---|---|
| `DATABASE_URL` | `postgresql://用户:URL编码密码@主机:端口/独立数据库`；按云数据库要求追加`?sslmode=require`等TLS选项 |
| `MILVUS_URI`、`MILVUS_TOKEN` | 基础设施提供的Endpoint及Token，不是图片对象存储地址 |
| `MILVUS_DATABASE` | 默认`default`；指定其他库前由管理员创建并授权 |
| `MILVUS_COLLECTION` | init自动生成独立前缀，后续保持稳定，不复用研发服务前缀 |
| `MILVUS_INDEX_TYPE` | 默认`HNSW`，度量固定`COSINE`；托管服务若只支持自动索引填写`AUTOINDEX` |
| `MODEL_BASE_URL`、`MODEL_API_KEY`、`MODEL_NAME` | 回答模型基础URL、Key、模型ID |
| `EMBEDDING_URL`、`EMBEDDING_API_KEY`、`EMBEDDING_MODEL` | 向量化完整URL、Key、模型ID |
| `RERANK_URL`、`RERANK_API_KEY`、`RERANK_MODEL` | 重排完整URL、Key、模型ID |
| `MODEL_DISABLE_THINKING` | 默认false，不附加供应商特定参数；服务明确支持时才设true |
| `MODEL_HTTP_ORIGINS` | 使用内网HTTP模型时填写准确的协议、主机、端口，多项逗号分隔；HTTPS无需此项 |
| `APP_HOST`、`APP_PORT` | 默认`127.0.0.1:8201`；异机网关或内网测试可设`0.0.0.0`，同时配置防火墙 |
| `ANONYMOUS_COOKIE_SECURE` | 正式HTTPS为true；HTTP测试为false |
| `FRAME_ORIGINS` | 实际父页面origin，不含路径；同源演示页可留空，不允许通配符 |

`init`只生成本地随机签名密钥、运维密钥、部署标识、Cookie名称和集合前缀，不创建数据库、不修改已有密码。重复执行保留非空配置。签名密钥、部署标识及Cookie名称投入使用后应稳定保管。

### 2.2 一键部署

确认数据库是本服务专用的空业务库、模型配置已填写：

```bash
sh scripts/external.sh deploy
```

脚本依次执行：

1. 检查必要配置，构建应用镜像，不构建或启动模型及数据库。
2. 检查PG及Milvus归属、文档和图片、三个模型接口；创建应用schema、表、检查点。
3. 调用Embedding解析入库，将知识正文和向量副本写入PG、向量索引写入Milvus。
4. 执行模型及索引检查。
5. 启动本项目App，等待ready，输出本机演示地址。

首次入库会产生Embedding用量，模型检查也会产生少量LLM、Embedding及Rerank用量。知识多或首次提取PDF图片时会等待数分钟，请根据终端阶段输出判断进度。

若已离线导入或已有兼容应用镜像，可以跳过构建：

```bash
sh scripts/external.sh deploy --image 本地应用镜像名称或ID
```

该镜像需要安装与本分支兼容的requirements.lock依赖。应用代码来自新目录挂载，不从旧目录运行。镜像选择会保存到本目录.env，后续start、restart继续使用它。

### 2.3 检查及平台接入

```bash
sh scripts/external.sh ps
sh scripts/external.sh doctor
sh scripts/external.sh documents
curl -fsS http://127.0.0.1:8201/smart-bot/ready
```

应用检查页：`http://服务器地址:8201/smart-bot/widget/anonymous-demo`。外部访问需要`APP_HOST=0.0.0.0`或实际网卡地址，且网络允许8201。正式接入推荐通过HTTPS网关，不直接公网开放数据库。

```html
<script src="https://客服实际域名/smart-bot/iframe-anonymous.js"></script>
```

网关示例见`deploy/nginx.conf.example`，将目标端口按实际改为8201或配置的端口。保留`/smart-bot`前缀、关闭SSE代理缓冲及缓存。配置`FRAME_ORIGINS`为平台页面origin。

## 3 在现有研发服务器独立测试

保留旧8200服务及原目录，另建测试目录：

```bash
cd ~/ai_customer
git clone --branch deploy-external-api-20261116 --single-branch \
  ssh://git@ssh.github.com:443/lsy199904/AI-customer-service.git \
  ai_customer_external
cd ai_customer_external

sh scripts/external.sh init \
  --from ../ai_customer_release/.env \
  --database ai_customer_external_test

sh scripts/external.sh deploy \
  --image "$(docker inspect --format '{{.Image}}' smarttitu-release-test)" \
  --create-database
```

这两步保留现有模型URL和Key、PG服务器地址与连接凭证、Milvus连接凭证，但将PG数据库改为`ai_customer_external_test`；新建随机Milvus集合前缀、身份密钥及Cookie名称，App使用8201、HTTP测试配置。不会复用旧业务库，不修改旧容器和旧.env。

`--create-database`是显式允许自动建库，仅使用所配置账号已有的CREATEDB权限，并连接同一PG服务器的`postgres`维护库执行CREATE DATABASE。没有权限或维护库不可访问时停止，请管理员创建并授权；不会更改账号权限或删除任何旧库。若数据库已经存在，会验证归属；已有客服数据但没有本部署归属标记时拒绝初始化。

创建独立测试库的管理员示例（按实际角色替换，不在普通应用账号里强行执行）：

```sql
CREATE DATABASE ai_customer_external_test OWNER 实际应用角色;
GRANT CONNECT, CREATE ON DATABASE ai_customer_external_test TO 实际应用角色;
```

测试地址：`http://服务器真实IP:8201/smart-bot/widget/anonymous-demo`，旧8200保持运行。接口沿用现有外部模型，因此测试和入库会消耗现有模型额度并共享其吞吐。新旧服务也共享PG、Milvus主机资源，建议避开业务高峰。

浏览器Cookie不按端口隔离，因此新入口使用独立Cookie名称，防止8200和8201互相覆盖匿名身份。测试环境不会自动继承旧聊天历史。

## 4 更新与异常处理

- 只改.env：`sh scripts/external.sh restart`，会重建App读取新配置，不是简单docker restart。
- 只改前端或Python代码且依赖不变：更新后执行`sh scripts/external.sh restart`。
- 修改依赖或Dockerfile：执行`sh scripts/external.sh deploy`重新构建。
- 修改知识文件：`sh scripts/external.sh ingest`，增量处理变化内容，不自动删除历史版本或清空数据库。
- 更换Embedding模型、URL或处理方式：先核对版本标识，再执行入库；不能把不同模型向量当作同一个空间混用。
- 停止新服务：`sh scripts/external.sh stop`，不会停旧容器或外部数据库。
- 查看启动日志：`sh scripts/external.sh logs`。
- 前置检查失败、入库失败或doctor失败时，不执行启动步骤。修正后重新执行deploy即可；未完成的知识发布不应当作成功。
- 部署使用目录锁`var/external-deploy.lock`防止同目录并行执行。若进程被强杀遗留锁，仅在确认没有部署进程后手工移除该空目录。
- 数据库归属标记记录部署标识与Milvus目标。不要复制整个新环境.env到另一套部署；不要手动删除标记绕过归属检查。目标变更需新建独立环境并验证。
- 不使用`down -v`、DROP TABLE、DROP DATABASE或删除集合处理部署失败。需要重置测试数据时由管理员单独确认处理。

## 5 验收及边界

上线前检查：新服务ready；三个API检查通过；常见知识问答、流式输出、配图和来源正确；独立浏览器不能读写对方会话；刷新后身份历史连续；日志写入新目录；原8200仍正常；备份和存储清理策略由部署方落实。

默认历史消息7天、运行日志30天、正文排障日志开启时3天；所有匿名用户共用企业滚动60秒20次额度。更换供应商后需重新验证召回阈值、重排阈值、模型输出及耗时，不能只验证连通。

本分支自动化仅针对Linux Docker Compose。Kubernetes、云数据库证书挂载、网关与防火墙由基础设施人员配置。宿主机仅需Python3，应用依赖由镜像提供；无外网时预先提供兼容镜像，使用--image。

自建五容器入口`compose.v3.yaml`和`scripts/v3.sh`为旧方案保留，不用于这条部署路线。本文之外的知识维护说明不改变部署入口。
