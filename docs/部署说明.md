# SmartTITU智能客服部署说明

适用分支：`deploy-external-api-20261116`。生产采用Kubernetes、外部模型API和云数据库；新建业务库并初始化，不迁移研发会话或数据库。本文为统一部署和更新入口。

## 一、部署准备

平台先开通以下资源，并确保App Pod与初始化Job可访问：

| 资源 | 要求及交付信息 |
|---|---|
| PostgreSQL | 16系列；提供地址、端口、TLS要求。准备专用业务库与账号，或提供有建库/建角色权限的管理员连接供脚本使用 |
| Milvus | 2.6系列；提供实际Endpoint、应用Token、业务数据库名和支持的索引类型；Serverless兼容性需实测 |
| 模型API | LLM、Embedding、Rerank三个接口，各自URL、Key、模型ID及协议。Embedding须兼容OpenAI embeddings，重排须兼容现有rerank请求/响应 |
| Kubernetes | 明确context、namespace权限、公司镜像仓库、镜像拉取凭证、默认或指定StorageClass；App上限2 CPU/4Gi，单副本，20Gi PVC |
| 网关 | 公司Ingress提供HTTPS域名，将`/smart-bot`原样转发至App Service的80端口，关闭SSE缓冲及缓存，配置足够的流式请求超时 |

云Milvus的etcd、MinIO由供应商管理，App不配置其接口。应用不新增Nginx容器。管理员需要创建namespace的权限；若namespace已建好，需该namespace中Secret、ConfigMap、Job、Deployment、Service、PVC、Pod的相应操作权限。

本仓库的“云端自动化”是在已开通实例中准备业务库和账号，不能替代特定云厂商的实例购买、VPC和白名单配置。

## 二、配置与镜像

在可访问镜像仓库与集群的部署终端拉取本分支，安装Python 3.10以上、kubectl和Docker。初始化只使用Python标准库，不在终端安装应用依赖。

```bash
sh scripts/production.sh init
chmod 600 .env
```

编辑生成的`.env`，不使用`source .env`。所有参数均有模板注释，重点如下：

| 参数 | 填写说明 |
|---|---|
| `DATABASE_URL` | `postgresql://业务账号:URL编码密码@PG地址:端口/独立业务库?sslmode=require`，以平台TLS要求为准 |
| `MILVUS_URI`、`MILVUS_TOKEN`、`MILVUS_DATABASE` | 平台提供的Endpoint、应用凭证、业务数据库名；不是etcd/MinIO地址 |
| `MILVUS_COLLECTION` | init自动生成独立集合前缀；投入使用后保持不变 |
| `MILVUS_INDEX_TYPE` | 自建环境通常HNSW；托管服务如仅支持自动索引，改为AUTOINDEX，按供应商确认 |
| `MODEL_BASE_URL`、`MODEL_API_KEY`、`MODEL_NAME` | LLM兼容接口基础地址，如`https://供应商/v1`，及Key、模型ID |
| `EMBEDDING_URL`、`EMBEDDING_API_KEY`、`EMBEDDING_MODEL` | 完整embeddings接口地址、Key、模型ID |
| `RERANK_URL`、`RERANK_API_KEY`、`RERANK_MODEL` | 完整rerank接口地址、Key、模型ID |
| `MODEL_HTTP_ORIGINS` | 内网HTTP模型接口需列出允许的origin，例如`http://10.180.158.23:4001`；HTTPS无需该项 |
| `ASSISTANT_IMAGE` | 公司仓库完整镜像地址和唯一版本标签，例如`registry.example.com/smarttitu/assistant:20261116-01`；不用latest |
| `K8S_CONTEXT`、`K8S_NAMESPACE` | 明确目标集群上下文及独立namespace；先用`kubectl config get-contexts`核对 |
| `K8S_PVC_NAME`、`K8S_STORAGE_CLASS` | 保存var的PVC及存储类型；已有PVC设`K8S_CREATE_PVC=false`并确保UID/GID 10001可写 |
| `K8S_IMAGE_PULL_SECRET` | 同一namespace内已创建的私有仓库拉取凭证名称，公共或已统一配置可留空 |
| `APP_PORT` | 容器监听端口默认8201，Service对内80；Pod独立网络，不会挤掉研发主机8200 |
| `ANONYMOUS_COOKIE_SECURE` | 生产HTTPS设true；研发HTTP设false |
| `FRAME_ORIGINS`、`CORS_ORIGINS` | 按实际平台页面origin配置，如`https://portal.example.com`；不要填URL路径 |

`AUTH_SECRET`采用系统安全随机数生成器生成48个随机字节并编码；`OPERATIONS_TOKEN`、`DEPLOYMENT_ID`及Cookie名称也自动生成。重复init保留已有非空值。后续发布沿用同一份.env，避免匿名身份、日志映射和部署归属改变。密钥进入Kubernetes Secret，不进入前端或Git；集群侧Secret读取权限与静态加密由平台管理。

构建并推送镜像（先登录公司仓库）：

```bash
sh scripts/production.sh build
```

镜像含完整应用依赖、`knowledge_sources/`、`app/static/media/`、`data/media.json`。生产无需挂载整个代码目录。`requirements.txt`是依赖声明，`requirements.lock`是镜像实际安装的固定依赖，`requirements-dev.txt`供测试使用。

## 三、云端业务数据库准备

PostgreSQL业务库与账号准备、`DATABASE_URL`格式、服务初始化九个部分的顺序依赖，以及全部可手动执行的建表SQL与归属标记生成方法，见专项文档 [PostgreSQL数据库初始化](PostgreSQL数据库初始化.md)。

平台已准备好专用业务库、账号和Milvus数据库时，可直接跳至第四节。应用账号需PG目标库CREATE权限，以创建`assistant`、`knowledge`两个schema。不要将管理员账号长期用作业务账号。

需要脚本自动准备时，先在.env填写计划使用的PG业务库名、专用账号、密码和实际连接地址；Milvus应用Token仍由平台签发。

```bash
sh scripts/cloud.sh init
# 编辑私有.env.cloud中的PG_ADMIN_URL；与DATABASE_URL指向同一实例及端口。
sh scripts/cloud.sh prepare
```

默认创建缺失的PG普通登录角色和以该角色为owner的独立数据库，不重置已有密码、不删除已有库。同名库归属其他角色或业务角色权限过高时停止。已有专用库仅验证时设置`CLOUD_PREPARE_PG=false`。

Milvus默认只检查平台分配的业务数据库与应用Token。平台支持create_database且需要脚本创建时，在.env.cloud设置`CLOUD_PREPARE_MILVUS=true`并填写`MILVUS_ADMIN_TOKEN`；否则保持false。Serverless不支持建库API时必须由控制台分配数据库。脚本不自动创建云IAM用户或推断Token权限，应用Token需有目标库内集合、索引、写入和检索权限。

脚本在目标集群启动一次性准备Job，完成后删除Job及临时管理员Secret。管理员配置仅在部署终端的私有.env.cloud保留，用后可移至受控凭证存储。普通App只获得业务凭证。

## 四、初始化并启动

```bash
sh scripts/production.sh render
sh scripts/production.sh deploy
sh scripts/production.sh status
sh scripts/production.sh logs
```

`render`输出`deploy/generated/kubernetes.json`供审阅，不含Secret或配置值；不要单独apply该文件绕过初始化顺序。

`deploy`顺序为：检查资源归属 → 准备PVC → 停止本部署旧Pod → 更新ConfigMap/Secret → 初始化Job连接PG与Milvus、检查知识配图和三个API、创建表 → 增量入库 → doctor验证 → 启动单副本App并等待ready。首次入库会调用Embedding产生向量；接口检查也有少量模型用量，不启动模型容器。

PG业务表、索引、知识表和LangGraph检查点由现有程序创建，无需手写字段。核心表包括`assistant.sessions/messages/rate_limits/tenant_message_limits/workflow_runs`、LangGraph检查点表、部署归属标记，以及`knowledge.rag_state/rag_documents/rag_revisions/rag_chunks/rag_events/rag_embedding_cache`。PG保存知识正文、修订与会话；Milvus保存对应知识编号及向量，集合和索引由入库自动创建。

同一套生产环境不要从多个终端或不同checkout同时发布。本地脚本提供单目录部署锁；不替代平台发布流水线的全局串行控制。

初始化失败不启动App，保留失败Job供排查；修正配置后重新执行相同命令。已有服务更新时会有维护窗口，失败后保持停止，避免新旧配置或向量混用。默认PVC为ReadWriteOnce，先停止旧Pod再运行初始化Job，App与Job共用同一var存储。不承诺无停机更新，不自动回退知识或数据库。

平台完成Ingress后验收：

```bash
curl -fsS https://实际客服域名/smart-bot/ready
curl -I https://实际客服域名/smart-bot/iframe-anonymous.js
```

浏览器访问`https://实际客服域名/smart-bot/widget/anonymous-demo`，检查提问、图片、引用、刷新历史及转人工；用两个不同浏览器验证历史隔离。前端接入脚本为`https://实际客服域名/smart-bot/iframe-anonymous.js`。

## 五、日常更新与维护

每次镜像内容变化使用新标签，先修改.env的`ASSISTANT_IMAGE`。更新前保存当前.env、镜像版本、PG备份和PVC快照；备份由平台策略执行。

| 变更 | 操作 |
|---|---|
| 新增/修改知识文档或图片登记 | 修改仓库中的`knowledge_sources/`、`app/static/media/`、`data/media.json`，设置新镜像标签，依次执行`production.sh build`、`production.sh update-knowledge` |
| LLM/Rerank地址、Key或模型ID调整；仅Embedding Key轮换 | 修改.env后执行`sh scripts/production.sh update-config`，检查后重建Pod，普通restart不会读取新环境变量 |
| Embedding地址、模型、版本或切片配置变化 | 修改.env、确认完整知识源仍在镜像，执行`sh scripts/production.sh update-knowledge --rebuild`；重新生成向量，会产生Embedding用量 |
| 应用代码/依赖更新 | 拉取代码、设置新镜像标签，执行`sh scripts/production.sh build`，再`sh scripts/production.sh update-app`；会做增量入库以检查镜像内知识兼容性 |
| 查看状态/运行日志 | `sh scripts/production.sh status`、`sh scripts/production.sh logs` |
| 停止应用 | `sh scripts/production.sh stop`；不删除数据库、PVC或外部服务 |

### 生产环境更新知识库

生产知识文档随应用镜像交付。不能只将文档上传到部署终端的目录后直接入库；必须先生成包含新文档的镜像，再执行更新。操作如下：

1. 将新增或修改的Word、PDF等正式知识文件放入项目的`knowledge_sources/`目录。更新已有文档时保持原文件名及相对路径，避免被登记为另一份文档；构建时应保留全部当前有效知识源。
2. 若涉及配图，同步更新`app/static/media/`中的图片及`data/media.json`中的登记；文档中的图片编号应与登记一致。仅修改文字且配图不变时，无需修改图片文件。
3. 在`.env`中将`ASSISTANT_IMAGE`修改为新的唯一版本标签，例如`registry.example.com/smarttitu/assistant:20261117-01`。按公司流程提交知识变更，确保部署终端构建的是已审核的版本。
4. 在项目根目录依次执行：

```bash
# 构建包含新文档、图片及登记信息的镜像，并推送公司镜像仓库。
sh scripts/production.sh build

# 使用新镜像执行初始化检查、增量入库、验证，再更新应用Pod。
sh scripts/production.sh update-knowledge

# 确认应用和初始化Job状态，并查看运行日志。
sh scripts/production.sh status
sh scripts/production.sh logs
```

普通更新不需要重新创建PG业务库、Milvus数据库，也不需要重新执行`cloud.sh prepare`。`update-knowledge`会复用现有数据库及部署身份，保留知识修订；无需手动删除表或集合。更新期间会短暂停止本部署应用，建议安排维护窗口；初始化失败时保持停止，修正后重试同一命令。

查看初始化Job的入库输出，核对`updated`、`unchanged`、`chunks`与doctor的`knowledge_count`，再通过前端验证修改过的问题、配图与引用。当前研发验证为4份文档、376条有效切片，仅作为该版本参考，不是固定验收数量；内容或切片方式变化时数量可以变化。内容与配置不变时，重复增量入库不应重复累加切片。

只有Embedding地址、模型、版本或切片配置变化时，才执行全量重建：

```bash
sh scripts/production.sh update-knowledge --rebuild
```

全量重建会产生Embedding用量。执行前确认镜像包含全部仍启用的知识源，并按平台策略备份PG和持久化数据。

从`knowledge_sources/`删除文件不会自动停用已入库知识。删除知识须先明确停用对应文档；停用或重命名应按知识维护流程处理，不能依靠删除源文件清除在线内容。

上述表格中的`production.sh`均位于`scripts/`目录。知识更新保留修订，重复增量入库复用已有Embedding缓存；不承诺零次接口调用。不自动停用从目录移除的文档；删除知识须先通过`manage.py deactivate 文档编号`明确停用。可由平台在停服维护期间使用同一镜像/配置/PVC运行管理Job，避免手工删除表或集合。

PG地址、MilvusEndpoint/数据库/集合前缀变化属于数据库迁移或新部署，不能仅按普通配置更新处理；归属检查会阻止误接其他数据。不要手动删除归属标记绕过校验。需要新环境时新建独立业务库与.env。

## 六、日志与持久化

运行路径与日志字段不变。容器内`/srv/assistant/var`对应20Gi PVC，包含：

- `var/logs/app-日期-进程号.jsonl`：普通运行日志，默认30天。
- `var/logs/conversations/年-月/tenant-…/user-…/session-….jsonl`：会话排障文件。本分支配置模板开启`LOG_DEBUG_CONTENT=true`，完整排障内容按`LOG_DEBUG_RETENTION_DAYS=7`保留7天，过期删除，不自动转摘要；设为false时仅记录摘要。
- 同目录`.lock`是文件锁，无正文属正常；不在运行时删除。
- `var/pdf_media/`：PDF提取的知识图片，长期保留，不按日志期限清理。

已有部署的真实.env不会被git pull或重复init覆盖。升级到本版本时，请在现有.env明确设置：

```dotenv
LOG_DEBUG_CONTENT=true
LOG_DEBUG_RETENTION_DAYS=7
```

研发执行`sh scripts/dev.sh restart`，生产执行`sh scripts/production.sh update-config`使配置生效。生产首次发布本次代码仍按代码更新流程构建新镜像后执行`update-app`。已被旧清理策略删除的内容无法恢复；清理在日志写入触发时执行，并非独立的定时任务。

在线历史仍保存在PG，默认7天，独立于文件日志。容器stdout由集群日志系统收集，轮转策略交由平台。PVC、PG和Milvus备份需分别配置；Git中没有实际运行日志或数据库内容。

## 七、研发服务器独立验证

可验证相同的业务库建表、归属保护、模型协议、知识入库、Milvus检索、图片与问答逻辑。无法代替生产云权限、TLS、网络、Kubernetes调度、存储和Ingress验收。旧8200服务不停止。

```bash
# 在新目录拉取本分支后执行，不能在旧服务目录覆盖配置。
sh scripts/dev.sh init --from ../ai_customer_release/.env --database ai_customer_external_test
# 检查.env：APP_PORT=8201，ANONYMOUS_COOKIE_SECURE=false。
# 账号有CREATEDB权限时可自动创建上述独立测试库；否则先请管理员创建并授权。
sh scripts/dev.sh deploy --create-database
sh scripts/dev.sh doctor
sh scripts/dev.sh documents
```

默认新建独立Cookie名称和随机Milvus前缀，复制旧模型接口但不复用旧业务库或签名密钥。HTTP访问`http://服务器IP:8201/smart-bot/widget/anonymous-demo`，防火墙需允许8201。已存在兼容应用镜像时可使用`sh scripts/dev.sh deploy --image 镜像名 --create-database`，但镜像必须包含本分支依赖；生产始终重新构建正式镜像。

若想完整验证“专用账号+业务库创建”流程：先`sh scripts/dev.sh build`，再`sh scripts/cloud.sh init`填写同机PG管理员连接，执行`sh scripts/cloud.sh prepare --docker`，随后`sh scripts/dev.sh deploy`。该入口运行同一`app.cloud`，不需要Kubernetes。仅使用独立测试库、专用普通账号，不填现有ai_customer库；默认演示复制出的管理员账号需换成计划创建的业务账号。

研发日常操作：

```bash
sh scripts/dev.sh restart          # .env更新后重新创建App
sh scripts/dev.sh ingest           # 知识增量更新
sh scripts/dev.sh ingest --rebuild # Embedding变更后重建
sh scripts/dev.sh stop             # 只停止新测试App
```

生产Kubernetes入口不使用`../deploy/compose/compose.dev.yaml`。研发host网络可使用127.0.0.1连接同机数据库；生产Pod内127.0.0.1只指向Pod自身，必须填写可从Pod访问的云Endpoint。

## 全局每日RAG额度

`GLOBAL_RAG_QUESTIONS_PER_DAY=1000`：同一业务数据库下所有企业、用户合计每日最多进入RAG 1000次，按北京时间零点切换日期。计数保存在`assistant.global_rag_daily_limits`，重启不会清零；多个App实例共享数据库时原子计数。常见问题固定答案不计入，问候、转人工等未进入RAG的路径不计入；进入RAG后即计数，检索失败或未命中也计入，已完成请求的相同请求编号重试不重复计数。达到上限后不再执行该次RAG模型调用，返回每日额度兜底，仍可点击常见问题或联系人工。推荐问题若再次进入RAG仍受额度限制。

现有`.env`可追加上述参数，不填时默认1000。研发执行`sh scripts/dev.sh restart`；生产更新ConfigMap并重建Pod（使用脚本时执行`sh scripts/production.sh update-config`）。首次发布代码需先更新应用镜像；新计数表自动创建，无需重新入库。`TENANT_MESSAGES_PER_MINUTE=20`仍独立生效，改为5即限制企业每60秒5次。每日次数限制用于控制调用数量，不等同精确金额封顶。

硅基流动Qwen3-32B：LLM基础地址填`https://api.siliconflow.cn/v1`、模型ID填`Qwen/Qwen3-32B`，设置`MODEL_DISABLE_THINKING=true`与`MODEL_THINKING_FORMAT=enable_thinking`；供应商Key填写对应API_KEY。原vLLM网关沿用`MODEL_THINKING_FORMAT=vllm`；不支持思考开关的模型选`none`，不自动按域名猜测。Embedding和Rerank地址、模型ID示例见`deploy/kubernetes/app.env.example`各自章节。更换Embedding接口/模型后按知识更新流程重新生成向量；仅换Key不需要重建。
