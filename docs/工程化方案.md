# 工程化方案（评审稿）

本文是代码结构、依赖管理、版本治理、容器化、PostgreSQL 迁移、Milvus 入库、双栈部署与 CI/CD 的整体工程化方案，供团队评审后分阶段实施。整体部署背景见[部署说明](部署说明.md)；现状数据库手工初始化流程见[PostgreSQL数据库初始化](PostgreSQL数据库初始化.md)（本方案落地后将由 Flyway 取代其 P4 阶段）。

- 适用分支：`deploy-external-api-20261116`
- 文档性质：目标态设计 + 落地路线，未实施前不代表现状
- 约束前提：生产运行于 Kubernetes，研发可用 Docker Compose；PostgreSQL 16 与 Milvus 2.6 由平台提供，本仓库不部署 PG/Milvus/etcd/MinIO 容器

## 一、现状评估

### 1.1 保留的优点（本方案不改动）

- 非 root UID 10001、`requirements.lock` 全量锁定纪律；
- K8s 探针齐全（startup/readiness/liveness 分离），`terminationGracePeriodSeconds: 190` 优雅退出；
- Init Job `backoffLimit: 0` + `doctor --models` 门禁；`ttlSecondsAfterFinished` 自动清理；
- `pg_advisory_xact_lock` + `external_deployment` 归属登记，防止误接管他人数据库；
- Milvus 集合按"前缀 + 配置指纹前 16 位"隔离，配置变更天然产生新集合、旧集合保留回滚；
- 生产镜像禁 `latest` 标签（`validate_image`）。

### 1.2 主要短板（本方案针对性解决）

| # | 问题 | 现状证据 |
|---|---|---|
| 1 | `app/core.py` 51KB 上帝模块；`manage.py` 单文件 CLI | Settings/Model/Service/Knowledge/auth 混居 |
| 2 | PG 无版本化迁移工具，升级路径空白 | `schema/1.0.0.sql` 注明"只用于新部署，不是升级脚本"；Python 建表与 SQL 文件两处维护同一 schema |
| 3 | K8s 清单由 Python 脚本从 `.env` 生成 | 环境间漂移、不可 diff 审阅、`deploy/k8s/prod` 为空目录 |
| 4 | 镜像单阶段构建、基镜像未按 digest 固定、无扫描/签名/SBOM | `Dockerfile` |
| 5 | 无 `pyproject.toml`；tests 目录 py/js 混排、无 pytest 配置；仓库内无 CI 定义 | `requirements-dev.txt` 仅 2 行 |
| 6 | 日志/图片落在 PVC 文件，锁死单副本 `Recreate` | `40-deployment.yml` 注释 |
| 7 | Milvus 旧指纹集合无生命周期管理 | `scripts/milvus/02_milvus.py` 只建不回收 |

## 三、依赖管理：uv（D1）

### 3.1 目标形态

| 现状 | 目标 | 说明 |
|---|---|---|
| `requirements.txt`（顶层范围约束） | `pyproject.toml [project.dependencies]` | 原样搬入范围约束 |
| `requirements.lock`（全锁定） | `uv.lock` | 跨平台通用锁、含哈希、提交入库 |
| `requirements-dev.txt` | `[dependency-groups] dev`（PEP 735） | 不进生产镜像 |
| `.venv/`（手工 pip） | `.venv/`（uv 托管） | uv 自动重建，PyCharm 解释器路径不变 |

### 3.2 pyproject.toml 骨架

```toml

    "fastapi>=0.115,<1", "uvicorn>=0.30,<1",

[dependency-groups]

[project.scripts]                      # §2.3 第 3 步启用

[build-system]

[tool.hatch.build.hooks.vcs]

[tool.pytest.ini_options]
```

### 3.3 迁移步骤（独立 chore 提交，不夹带功能）

```bash
# 1. 固定 uv 版本（开发机与 CI 一致）
# 2. 范围约束搬入 pyproject 后生成锁
uv lock
# 3. 【关键】新旧解析对照
uv export --format requirements-txt --no-hashes -o /tmp/uv-resolved.txt
diff <(sort /tmp/uv-resolved.txt) <(sort requirements.lock)
```

对照处理原则：补丁版漂移→接受并跑 `uv run python manage.py check` 冒烟；minor 漂移→临时收紧为 `==当前锁定版` 再放松，避免迁移提交夹带行为变化；`httpcore2/httpx2/langchain-protocol` 等冷门包优先排查是否解析成功。此后删除 `requirements.*` 三文件。

### 3.4 命令映射

| 场景 | 旧命令 | uv 命令 |
|---|---|---|
| 本地开发环境 | `pip install -r requirements-dev.txt` | `uv sync` |
| 校验锁未私改 | — | `uv sync --frozen`（CI 必用） |
| 运行应用 | `python -m app.server` | `uv run python -m app.server` |
| 升级依赖 | 改 txt → 重新 lock | `uv lock --upgrade`（单独 chore PR） |

规则：凡改依赖必须经过 `uv.lock` diff；禁止手改 `requirements.*`。

## 四、语义化版本（D2）

### 4.1 治理规则

| 变更类型 | 版本动作 |
|---|---|
| API 契约不兼容、PG schema 不可回退、Milvus 集合结构变更 | major |
| 新功能 | minor |
| 缺陷修复、依赖补丁 | patch |
| uat 验证版 | `vX.Y.Z-rc.N`（仅 uat overlay 引用） |

配套纪律：**Flyway 迁移必须向后兼容上一个 minor 的镜像**（支持 `rollout undo`）；不兼容变更升 major 并在发布说明标注"不可回滚"。镜像同时打 `vX.Y.Z` 与 `vX.Y.Z-{git_short_sha}`，生产 overlay 引用 digest。

### 4.2 版本单一事实源

推荐 git tag 派生（§3.2 已含 hatch-vcs 配置）：`git tag v1.2.3` → `uv build` 产物版本即 1.2.3；未打 tag 得 `X.Y.Z.devN+gSHA` 开发态。备选：静态 version + CI 校验 tag == pyproject。

### 4.3 版本可见性链路

```
git tag v1.2.3
  → CI --build-arg APP_VERSION=1.2.3
      → 镜像 OCI label: org.opencontainers.image.version
      → titu.__version__（_version.py 生成；源码运行态回退环境变量 APP_VERSION）
          → /smart-bot/ready 响应体 "version" 字段
          → manage.py check / doctor 输出
          → 启动日志 version=1.2.3, deployment=<id>
          → external_deployment.metadata 记录 app_version / schema_version
```

### 4.4 发布流程

```
1. git tag v1.2.3 → 触发流水线
2. check（ruff/pytest unit）→ build（uv sync → uv build → docker build）→
   trivy 扫描（HIGH/CRITICAL 阻断）→ syft SBOM → cosign sign → push 两个 tag
3. deploy-dev：db-migrate Job → ingest Job → apply → rollout → 冒烟（ready 核对 version）
4. promote uat（overlay 改 digest，手动）
5. prod（手动审批）；CHANGELOG.md（Keep a Changelog）随 tag 提交
```

## 五、容器化（D5）

### 5.1 多阶段 Dockerfile（uv 官方模式）

```dockerfile
# syntax=docker/dockerfile:1.7
FROM python:3.12-slim@sha256:<pin> AS builder
COPY --from=ghcr.io/astral-sh/uv:<ver>@sha256:<pin> /uv /uvx /usr/local/bin/
ENV UV_COMPILE_BYTECODE=1 UV_LINK_MODE=copy
WORKDIR /build
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev --no-install-project     # 依赖层：源码改动不击穿

FROM python:3.12-slim@sha256:<same-pin>
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1 HOST=0.0.0.0 PORT=8000
RUN apt-get update && apt-get install -y --no-install-recommends libgl1 libglib2.0-0 libgomp1 \
 && rm -rf /var/lib/apt/lists/* && useradd --uid 10001 --create-home assistant
COPY --from=builder /build/.venv /srv/assistant/.venv
WORKDIR /srv/assistant
COPY app ./app
COPY database ./database                               # Flyway 迁移 SQL 随镜像交付（§6.4 依赖）
COPY data ./data
COPY knowledge_sources ./knowledge_sources
COPY manage.py ./
USER 10001:10001
ENV PATH="/srv/assistant/.venv/bin:$PATH"
EXPOSE 8000
CMD ["python", "-m", "app.server"]
```

要点：运行镜像不含 uv 本体；apt 库是 opencv/rapidocr 运行时依赖留在 runtime 层；内网私有 PyPI 需在 Dockerfile 与 CI 两处配置 `UV_INDEX_URL`。

### 5.2 供应链门禁

标签规则 `{semver}-{git_short_sha}`；trivy 扫描 HIGH/CRITICAL 阻断；syft SBOM 归档；cosign 签名；生产 overlay 引用 digest；`flyway/flyway` 等第三方工具镜像同步入公司 Harbor 并纳入扫描；基镜像 digest 每季度评审。

## 六、PostgreSQL 版本管理：Flyway（D3/D8）

### 6.1 选型说明

满足工具化四底线：**状态表**（`flyway_schema_history`）、**顺序链**（revision 顺序 + 分支冲突检测）、**失败恢复**（PG 下每迁移独立事务，失败全回滚、history 不留失败行，修正文件即可重跑）、**门禁自动化**（`migrate` + 退出码）。纯 SQL 文件贴合 DBA 审阅流程。

代价与对策：JVM 容器形态（团队无需装 Java，镜像 Harbor 内化）；JDBC URL 与 `DATABASE_URL` 格式差异（CI 转换，§6.5）；Undo/按文件关事务为 Teams 付费（forward-only 策略下不需要；并发索引用 §6.6 窗口方案规避）。

### 6.2 目录与文件规范

```text
database/postgres/
├── flyway.conf                # 仅非敏感默认值（locations/schemas/validateOnMigrate）
└── migrations/
    ├── V1.0.0__baseline.sql   # schema/1.0.0.sql + data/1.0.0.sql 合并转换（基线单文件）；external_deployment 由 claim 负责
    └── V1.1.0__<desc>.sql     # 后续增量：版本号 = 引入该变更的应用版本
```

目录按"数据库类型"组织（`database/postgres/`），不绑定迁移工具名：未来新增其他数据源的初始化/迁移脚本有固定归置（如 `database/<type>/`）；`FLYWAY_LOCATIONS` 固定指向 `migrations/`，`flyway.conf` 与迁移同级。与冻结归档的 `scripts/postgres/`（旧手工 SQL）路径上明确区分。

编号规则：`V<应用版本>__描述.sql`，一个版本内多个 schema 变更**合并一个文件**（一个发布 PR 一个迁移）。备选：独立递增整数 `V3__...`（零冲突但与应用版本脱钩），二选一。

**`1.0.0.sql` 转换五规则**：

1. 删 `BEGIN;`/`COMMIT;`——Flyway 自带事务，显式事务控制会报错；
2. `SET LOCAL search_path` 改为文件头一次 `SET search_path TO assistant,public;`；**新增迁移一律全限定名**（`assistant.messages`）；
3. 删开头 `DO $manual$` 外来表检查块——职责移交 Python claim（§6.4）；
4. 去 `IF NOT EXISTS`（保留 `CREATE SCHEMA IF NOT EXISTS`）——工具保证一次执行，防御式写法掩盖漂移；
5. `assistant.external_deployment`（归属登记表）及登记行**不进迁移**——由 claim 在 migrate 前创建并写入（deployment 专属元数据），兼作发布门禁失败重试的所有权凭据；因此验收 diff 需先执行 claim。

DML（种子/字典/回填）一律走 versioned 迁移，禁止运行时 INSERT。**已应用的 V 文件永不修改**（checksum 校验 fail；误改仅限 `repair` 修复场景）。

### 6.3 基线策略

```text
存量环境（已有 1.0.0 schema）：
  flyway -baselineVersion=1.0.0 -baselineDescription="1.0.0 schema" baseline
  → 只写基线行不执行 SQL；此后 migrate 只应用 >1.0.0 增量

全新环境：
  flyway migrate → V1.0.0 全量建库 + 种子，一步到位
```

**禁止 `baselineOnMigrate=true`**：它会对"非空但无 history"的库静默收编，与 `external_deployment` "未登记即拒绝接管"的安全语义冲突。外来库防护留在 claim 步骤，Flyway 永不接触未 claim 的库。基线为一次性运维动作，命令记录进数据库初始化文档（重写版），执行前后各 `pg_dump` 快照。

### 6.4 发布门禁链（Init Job 拆分）

```text
Job-1  db-migrate（新）
  initContainer claim-and-copy-sql（应用镜像，与应用同 tag）:
      python -m titu.ops claim            # advisory lock + 归属校验 + marker 写入(app_version/schema_version)
      cp -r /srv/assistant/database/postgres/migrations/. /migrations/
  container flyway（flyway/flyway，Harbor 内化，digest 固定）:
      args: ["-connectRetries=10","migrate"]
      SQL 来自 emptyDir 卷（readOnly）
  → CI: kubectl wait --for=condition=complete，失败终止发布

Job-2  app-ingest（原 Init Job 裁剪 initialize 段）
  python manage.py ingest && python manage.py doctor --models
```

Job 骨架：

```yaml
apiVersion: batch/v1
kind: Job
metadata: { name: titu-db-migrate, namespace: app-zone }
spec:
  backoffLimit: 0
  ttlSecondsAfterFinished: 86400
  activeDeadlineSeconds: 1800
  template:
    spec:
      restartPolicy: Never
      automountServiceAccountToken: false
      initContainers:
        - name: claim-and-copy-sql
          image: harbor.rd.dsi/smarttitu/assistant:v1.2.0     # CI 写入，与应用同版本
          command: ["sh","-ec","python -m titu.ops claim && cp -r /srv/assistant/database/postgres/migrations/. /migrations/"]
          envFrom:
            - configMapRef: { name: titu-assistant-config }
            - secretRef:    { name: titu-assistant-secret }
          volumeMounts: [{ name: migrations, mountPath: /migrations }]
      containers:
        - name: flyway
          image: harbor.rd.dsi/third-party/flyway:11.x.x      # digest 固定
          args: ["-connectRetries=10","migrate"]
          env:
            - { name: FLYWAY_URL,       value: "jdbc:postgresql://…?sslmode=require" }
            - { name: FLYWAY_USER,      valueFrom: { secretKeyRef: { name: titu-assistant-secret, key: PG_USER } } }
            - { name: FLYWAY_PASSWORD,  valueFrom: { secretKeyRef: { name: titu-assistant-secret, key: PG_PASSWORD } } }
            - { name: FLYWAY_LOCATIONS, value: "filesystem:/migrations" }
            - { name: FLYWAY_SCHEMAS,   value: "assistant,knowledge" }
            - { name: FLYWAY_VALIDATE_ON_MIGRATION, value: "true" }
          volumeMounts: [{ name: migrations, mountPath: /migrations, readOnly: true }]
      volumes: [{ name: migrations, emptyDir: {} }]
```

设计要点：**SQL 与应用镜像同版本交付**（claim 容器从应用镜像拷出），杜绝迁移与镜像版本错位；Flyway 迁移期自带 PG advisory lock，双 Job 并发误触发安全；`app.deployment` 剥离建表/种子逻辑只保留 claim——建表权收归 Flyway，消灭 Python 与 SQL 双处维护；claim 增写 `schema_version` 到 marker 元数据供对账。

研发/CI 本地执行统一走 `scripts/db.sh`（docker run 封装 `migrate|validate|info|baseline`）。

### 6.5 JDBC URL 转换

```text
postgresql://user:pass@pg.host:5432/business?sslmode=require
  → jdbc:postgresql://pg.host:5432/business?sslmode=require（凭据剥离走 FLYWAY_USER/PASSWORD）
```

CI 渲染 Job 时脚本转换（kustomize 无字符串变换能力）；`db.sh` 同样调用；转换单元测试进 `tests/unit`。

### 6.6 PG 特有事项

1. **事务模型**：每文件一个事务，失败全回滚、可修文件重跑；
2. **`CREATE INDEX CONCURRENTLY`**：不能进事务、Community 不能按文件关事务；当前部署为 **Recreate（升级窗口应用已停）**，升级期直接用普通 `CREATE INDEX`；未来切 RollingUpdate 多副本后再评估停写窗口或 Teams 版；
3. **大表回填**：plpgsql 批处理循环（`LIMIT 5000 FOR UPDATE SKIP LOCKED`）写单迁移文件，幂等可重跑；量级更大走带外脚本 + 人工窗口；
4. **回滚策略**：无 undo，与 D2 纪律一致——迁移兼容上一 minor 镜像，回滚 = `rollout undo`，数据库只前进；不兼容变更升 major 并标注。

## 七、Milvus 初始化与知识入库

### 7.1 保留的设计

"集合名 = `MILVUS_COLLECTION` 前缀 + 配置指纹前 16 位"即行业 index versioning：Embedding 模型/维度/切分参数任一变化 → 新集合，旧集合天然保留回滚；建集合脚本"字段不一致即拒绝，不覆盖"语义正确。

### 7.2 收敛与生命周期

1. `scripts/milvus/02_milvus.py` 的 create/verify 并入 `titu vectors ensure`（脚本保留薄封装）；
2. `ingest` 开头加 `pg_advisory_lock(hashtext('milvus-ingest:'||deployment_id))`，防止 Init Job 与人工操作并发写集合；
3. 新增 `titu vectors gc --older-than 7d --dry-run`：列出当前部署 claim 之外的旧指纹集合，`--confirm` 后删除；K8s CronJob 月度 + 人工确认，**禁止部署流程自动删除**（回滚窗口安全第一）；
4. 知识指纹额外写入 `external_deployment.metadata`（knowledge_bundle_digest、文件数）；`doctor` 校验"镜像内知识 ≠ 数据库登记知识"告警；镜像重建而知识未变时指纹不变、不重入库。

发布链中入库时点：`db-migrate` 通过后 `app-ingest` Job 执行 `ensure → ingest → doctor --models`，全过才放行 rollout。

### 8.2 发布编排（单副本 Recreate 维持）

```text
1. push 镜像（sha tag + semver tag）
2. apply job-migrate → wait complete → 失败终止（旧版未动）
3. apply job-ingest  → wait complete（ensure/ingest/doctor 门禁）
```

### 8.3 Compose 双角色

- `compose.dev.yaml`：维持现状（仅 App、外部 PG/Milvus），`scripts/dev.sh` 后端；
- `compose.e2e.yaml`：CI 专用，起 postgres:16 + milvus 2.6 standalone 跑 `tests/{integration,e2e}`（内网 Harbor 环境比 testcontainers 更可控）；
- 应用代码不感知部署方式（配置全走环境变量），双栈共用同一镜像、同一命令集。

### 8.4 可观测性与多副本演进

- 日志：PVC 文件保留（合规留存），同时 stdout JSON 行接集群日志（Loki/ELK）；
- 指标：新增 `/smart-bot/metrics`（prometheus_client），暴露问答延迟、RAG 召回耗时、配额水位；
- 多副本三前提：日志主走 stdout、`pdf_media` 迁对象存储或 RWX、限流/配额已全在 PG（满足）→ Deployment 改 `RollingUpdate maxUnavailable:0` + HPA（CPU 70%）；届时 `tenant_message_limits` 滚动窗口评估 PG 行锁竞争。

## 九、CI/CD 流水线


## 十一、验收标准

1. **依赖**：`uv sync --frozen` 一条命令在本地/CI/镜像三端装出完全一致环境；任何依赖变更可从 `uv.lock` diff 审阅。
2. **版本**：`/smart-bot/ready`、`doctor`、镜像 label、`external_deployment.metadata` 四处版本一致；tag 即版本，无人工同步点。
3. **数据库**：任何环境 `flyway info` 能回答"在哪个版本、哪些待执行"；从零库到可用只靠 `migrate` 一条命令；升级失败重跑安全；存量环境已 baseline 登记。
4. **发布**：迁移与入库先于新 Pod，任一门禁失败即终止发布且旧版无损；回滚仅 `rollout undo`，数据库不回退。
5. **镜像**：digest 可追溯到 SBOM 与签名；生产清单无浮动标签。
6. **知识**：`doctor` 能发现镜像知识与登记知识不一致；旧集合 GC 必须人工确认。
