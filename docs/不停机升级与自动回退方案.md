# 不停机升级与失败回退

> **状态（2026-11-20）**：阶段一（停机更新 + 失败回退）已闭环；阶段二、三未实施，需要基础设施与代码改动。回退动作是手工命令（`rollout undo` / `scale`），不引入额外的发布脚本，命令见 `deploy/k8s/dev/README.md`。
> 相关文件：`deploy/k8s/dev/60-deployment.yml`、`deploy/k8s/dev/README.md`（发布步骤与失败恢复）、`deploy/k8s/dev/30-pvc.yml`、`app/rag.py`、`app/core.py`。

## 0. 结论先行

「不停机」和「失败回退」是两个独立能力，先拆开看：

| 目标 | 现状 | 缺口 |
|---|---|---|
| 停机更新（允许中断，失败可恢复） | ✅ 已闭环 | 无；窗口 = migrate + ingest + 启动时间 |
| 升级失败回退 | ✅ 已具备 | 探针提供失败判定 + 手工 `rollout undo`（步骤见 README「失败恢复与回退」） |
| 应用代码升级不停机 | ❌ 不能 | 需阶段二：media 拆卷 + 2 副本 + RollingUpdate |
| 知识内容更新不停机 | ❌ 不能 | 同阶段二（有短暂的媒体 404 窗口） |
| Embedding/解析配置变更不停机 | ❌ 不能 | 需阶段三：`rag_state` 与激活指针按 fingerprint 分区 |
| 破坏性 SQL 变更不停机 | ❌ 不能 | 靠 expand-contract 拆成两次发布，不是技术问题 |

一句话：**失败回退今天就能用（探针判失败 + 一条 `rollout undo`）；真正不停机要先解决"一块 RWO 卷卡住所有 Pod"这个物理约束。**

---

## 1. 现在为什么做不到

### B1　单副本 + Recreate + RWO 卷

`60-deployment.yml` 是 `replicas: 1` + `strategy: Recreate`，`30-pvc.yml` 是 `accessModes: ["ReadWriteOnce"]`。

RWO 的语义是"同一时刻只能挂在一个**节点**上"。滚动更新要求新旧 Pod 并存，而新 Pod 必须等旧 Pod 释放卷才能启动，所以物理上不可能重叠——这就是 `Recreate` 存在的原因，也是停机的直接来源。

### B2　一块卷里混了三种性质不同的数据

| 目录 | 谁写 | 能否多 Pod 共享 |
|---|---|---|
| `var/pdf_media` | 只有知识初始化 Job | ✅ 只读共享安全（文件名是内容哈希） |
| `var/logs` | App 自己写 | ❌ 两个进程追加同一文件会串行交错 |
| `var/assistant.db`、`var/rag.sqlite3` | App 写（PG 未配置时的回退） | ❌ SQLite 单写者，NFS 上文件锁不可靠 |

三种混在一块，导致"这块卷能不能共享"没有干净答案，只能整块独占。**这是唯一必须动基础设施才能解的阻塞。**

### B3　探针全部被注释

原 `60-deployment.yml` 的 `startupProbe/readinessProbe/livenessProbe` 都是注释状态。后果是 `kubectl rollout status` 只要看到容器 Running 就判成功，**没有"其实服务不了"的信号，失败回退就无从判断**。

本次已启用，并把启动探针和就绪探针分开：

- `startupProbe` → `/smart-bot/health`：只判进程活着。若拿 `/ready` 当启动探针，知识未入库时 Pod 会被反复重启。
- `readinessProbe` → `/smart-bot/ready`：真门禁。`app/server.py` 的 `/ready` 会 `SELECT 1`、检查知识行数非空、检查 Milvus 集合存在，失败返回 503。失败只摘流量不重启，Deployment 到 `progressDeadlineSeconds` 判失败。
- `livenessProbe` → `/smart-bot/health`：只处理"进程卡死"，不因依赖故障重启。

### B4　`rag_state` 单行，fingerprint 天然互斥

```sql
-- app/rag.py
CREATE TABLE IF NOT EXISTS rag_state(id INTEGER PRIMARY KEY CHECK(id=1), fingerprint TEXT, generation INTEGER NOT NULL);
```

`app/rag.py` 的 `snapshot()` 把激活状态硬编码在 `id=1` 这一行上：

```python
state = dict(db.execute('SELECT * FROM rag_state WHERE id=1').fetchone())
rows  = db.execute('SELECT ... FROM rag_chunks c JOIN rag_documents d ON d.id=c.document_id AND d.current_revision=c.revision WHERE d.active=1')
```

而 `_assess` 里有一道硬校验：`state['fingerprint'] != c.fingerprint` 就抛 `RAGError('当前Embedding配置与索引不一致,请先重建')`。

所以只要新版本的 fingerprint 变了：

1. 新 Pod 的 Milvus 集合名变了 → `/ready` 503，永远不就绪；
2. 一旦 ingest 把 `rag_state.fingerprint` 改成新值 → 旧 Pod 下一个请求直接 500。

两边不能同时活着，**这类升级只能硬切**。这不是 K8s 配置能解决的，必须改数据模型。

## 2. 变更类型 → 可行矩阵

| 变更 | fingerprint | 能否不停机 | 前置条件 |
|---|---|---|---|
| 应用代码、依赖小版本、配置值 | 不变 | ✅ 阶段二 | media 拆卷 + 2 副本 |
| 新增/修改知识文档 | 不变 | ⚠️ 可，但有短暂媒体 404 | 同上；旧 Pod 缺新图 |
| Embedding 模型/维度/切片参数 | 变 | ❌ | 阶段三 |
| 解析器版本（`parser_revision`） | 变 | ❌ | 阶段三 |
| 加表/加列/加索引 | — | ✅ | 迁移只做 expand |
| drop/rename 列、改类型 | — | ❌ | 拆两次发布：先双写兼容，再删 |

## 3. 阶段一：门禁与失败回退（已落地）

### 3.1 Deployment 增加的门禁参数

```yaml
revisionHistoryLimit: 5      # rollout undo 要能找到上一版 ReplicaSet
minReadySeconds: 10          # 就绪后再观察 10s，挡住"起来就崩"的版本
progressDeadlineSeconds: 900 # 15 分钟未完成即判失败，与发布命令的 --timeout 对齐
```

### 3.2 发布执行链（手工执行）

命令逐条写在 [`deploy/k8s/dev/README.md`](../deploy/k8s/dev/README.md) 的「发布步骤」，不再额外封装发布脚本，避免脚本与文档两套顺序各自漂移。

```text
预检（命名空间 / 当前镜像 / 目标镜像）
  → scale 0 停 App，等 Pod 真正消失（释放 RWO 卷）
  → db-migrate Job（查 Complete/Failed 条件，失败立即停止，不白等到超时）
  → 知识初始化 Job（同上）
  → 删知识 Job 并等 Pod 退出（它也挂着同一块卷）
  → apply Deployment
  → rollout status --timeout=900s   ─┐
  → 冒烟 /smart-bot/ready           ─┴─ 任一失败 → rollout undo → 等就绪 → 复验
```

**停 App 必须在两个 Job 之前**。知识 Job 要挂 `titu-assistant-var`（RWO），App 还在跑时 Job 可能因 `Multi-Attach` 挂不上，或者被调度到同节点后与 App 并发写 `var/`。先停再跑，卷一定空闲；发布步骤要求 `kubectl get pod` 列表为空才继续，Pod 没退出就中止。

**两种失败不能混用同一种恢复方式**：

| 失败阶段 | Pod 模板 | 恢复动作 | 原因 |
|---|---|---|---|
| db-migrate / 知识 Job | 仍是旧版 | `scale --replicas=1` | 镜像还没换，只需把副本拉回来；此时 `rollout undo` 会退到更早的版本 |
| apply 之后（就绪失败 / 冒烟失败） | 已换新版 | `rollout undo` + 等就绪 + 复验 | 需要把模板退回上一版 |

冒烟不是 `curl` 宿主机域名，而是 `kubectl exec` 进 Pod 里请求 `127.0.0.1:8201`：不依赖 Ingress/DNS 是否已配好，也不依赖镜像里有 `curl`（用镜像自带的 python）。

首次发布没有上一版，`rollout undo` 会报 `no rollout history found`，只能修好原因重发。

### 3.3 回退边界（必须写进纪律）

- **回退的是应用，不是数据库。** Flyway 没有自动 undo。`rollout undo` 把 Pod 模板退回上一版，数据库停在新 schema 上，所以**每个迁移必须能被 N-1 版本应用使用**：只加不删、加列必须有默认值或可空、不改列类型、索引用 `CREATE INDEX`（新库）/`CONCURRENTLY`（存量库）。
- `flyway.ignoreMigrationPatterns=*:future` 已配置，保证旧镜像看到"数据库版本比自己新"时 `validate` 不拦。
- 破坏性变更拆两次发布：第 N 版停写旧列、第 N+1 版删列。中间不允许跳版回退。
- **ConfigMap / Secret 不在发布步骤里**。发布步骤只 apply 两个 Job 和 Deployment；改了配置文件要先单独 apply，否则 Job 与 App 都读集群里的旧值。`rollout undo` 也不会还原配置，回退时需手工改回并重新 apply。
- **知识库通常不需要回退**。`fingerprint` 变化时 `ingest_documents()` 在写任何数据之前就抛错（`app/rag.py`），知识库保持原状，旧镜像可以直接启动。唯一例外是有人手工跑过 `ingest --rebuild`：此时 `rag_state.fingerprint` 已改写，回退镜像后 `/ready` 会返回 `index_mismatch`，必须用旧镜像重跑一次知识 Job。

### 3.4 阶段一的能力边界

已有完整的停机更新闭环：停 → 迁移 → 入库 → 起 → 验 → 失败恢复。停机窗口 = migrate + ingest + 启动时间，与 `Recreate` 的窗口相同。对当前单副本结构来说，这已经是能做到的上限。

不能覆盖的三类：跨版本滚动（需要阶段二）、`fingerprint` 变化的平滑切换（需要阶段三）、破坏性 SQL 的单次回退（只能拆发布）。另外，`fingerprint` 变更的发布会在知识 Job 阶段失败，因为发布流程不传 `--rebuild`；这是有意的——重建会重写全部向量并消耗大量 Embedding 额度，必须人工确认。

## 4. 阶段二：拆卷 + 滚动更新（真·不停机）

### 4.1 先把卷拆成三块

| 内容 | 目标载体 | 访问方式 |
|---|---|---|
| `pdf_media` | 独立 PVC `titu-assistant-media`（RWX）或对象存储 | App **只读**，Job 读写 |
| `logs` | `emptyDir` | 每 Pod 自己写自己 |
| `assistant.db`/`rag.sqlite3` | `emptyDir`，并强制要求 `DATABASE_URL` | 生产用 PG，不再保留 SQLite 回退 |

只有第一步解决了"App 不写共享卷"，滚动更新才成立。`pdf_media` 的文件名是 `pdf-<sha256前32位>`（`app/pdf_media.py` 的 `asset_id`），写入走 `uuid.tmp` + rename，天然幂等，多 Pod 只读没有一致性问题。

### 4.2 关键清单改动

```yaml
replicas: 2
strategy:
  type: RollingUpdate
  rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }   # 先起新再停旧
spec.template.spec:
  terminationGracePeriodSeconds: 190                   # 保持，长回答要收尾
  containers:
    - lifecycle:
        preStop: { exec: { command: ["sleep", "10"] } }  # 等 endpoints 摘除，避免最后几个请求打空
      env:
        - { name: PDF_MEDIA_DIR, value: /srv/assistant/media }
        - { name: LOG_DIR,       value: /srv/assistant/logs }
      volumeMounts:
        - { name: media, mountPath: /srv/assistant/media, readOnly: true }
        - { name: logs,  mountPath: /srv/assistant/logs }
  volumes:
    - name: media
      persistentVolumeClaim: { claimName: titu-assistant-media, readOnly: true }
    - name: logs
      emptyDir: {}
```

配套：

- `PodDisruptionBudget`：`minAvailable: 1`，防止节点维护时把两个副本一起驱逐。
- 启动断言：`DATABASE_URL` 为空时直接退出。SQLite 挪到 `emptyDir` 后如果不校验，会安静地写到一个重启即丢的目录里。
- 镜像 tag 必须每次不同。`IfNotPresent` + 同名 tag 覆盖推送，节点上不会重新拉取。

### 4.3 阶段二仍然解决不了的两件事

1. **媒体目录仍是启动时扫描。** `self.media.include_generated(config.pdf_media_dir)` 只在 `Service.__init__` 执行（`app/core.py`），所以 Job 写入的新图，滚动中已经在跑的旧 Pod 看不到，`/media/pdf-*.png` 会 404。文字答案正常，只是配图缺失。
2. **知识更新期间的短暂不一致。** ingest 先写 PG 的 `rag_documents.current_revision`，再切 Milvus 向量（或反之），新 Pod 与旧 Pod 可能短暂看到不同版本的切片集合。

要彻底消除，需要把"激活指针"也做成版本化——就是阶段三。

## 5. 阶段三：按 fingerprint 分区（配置变更也能不停机）

现在的数据模型是"全局唯一激活状态"：

```text
rag_state(id=1)                          -- 只能存在一个 fingerprint
rag_documents.current_revision           -- 全局唯一激活版本
rag_chunks(document_id, revision)        -- 按 revision 存
```

改法（不是配置开关，是数据模型重构）：

1. `rag_state` 主键改为 `fingerprint`，`generation` 跟着每一行走；ingest 写新行，不碰旧行。
2. 新增 `rag_active(fingerprint, document_id, revision)`，替代 `rag_documents.current_revision`；`snapshot()` 按当前进程的 fingerprint 取激活集。
3. `_assess` 找不到自己的 fingerprint 行时返回 503 而不是抛 `RAGError`——让它表现为"未就绪"，而不是"线上报错"。

改完之后：

- 新版本用新 fingerprint → 新集合、新激活指针，**与旧版本完全隔离**，可以慢慢预热；
- 切换 = 改镜像 tag，回退 = 改回来，**知识数据一行都不用动**；
- 旧 fingerprint 的行与集合按保留策略清理，不再需要"重建即破坏"。

这一步做完，才谈得上"任何升级都不停机"。

## 6. 回退矩阵

| 层 | 出问题怎么退 | 能否自动 | 备注 |
|---|---|---|---|
| 应用镜像 / Pod 模板 | `kubectl rollout undo` | ⚠️ 手工一条命令 | 探针给出失败信号，回退动作由人执行；依赖 `revisionHistoryLimit` |
| SQL schema | 不回退 | — | 靠 expand 纪律 + `*:future` |
| 知识（PG + Milvus） | 不回退 | — | 只增不删；`fingerprint` 变化时 ingest 写入前报错，库保持原状 |
| 媒体文件 | 不回退 | — | 文件名是内容哈希，只增不删 |
| ConfigMap / Secret | 按备份还原后重新 apply | ⚠️ 手工 | `rollout undo` 不覆盖它们 |
| 镜像仓库里的坏 tag | 无需处理 | — | 回退只改 Deployment 引用 |

`ConfigMap` 这一行是最容易漏的：改了 ConfigMap 再 `rollout undo`，退回去的 Pod 读到的还是**新**配置。要真正做到"一键回到上一版"，配置也得进版本化命名或 GitOps 管理的不可变对象。

## 7. 验收标准

阶段一：

- [ ] 故意推一个启动即崩的镜像，按 README 第 5 步观察 `progressDeadlineSeconds` 到点判定失败，执行 `rollout undo` 后 `/ready` 返回 200。
- [ ] 故意让 `/ready` 返回 503（清空知识或改错 Milvus 集合名），确认 Pod 保持 `Running` 但 `0/1 Ready`，服务不打流量，且不被 liveness 重启。
- [ ] 故意让 db-migrate Job 失败（写错 SQL），确认**没有** apply 新镜像，而是把旧版本 `scale` 回 1 并复验通过；`rollout undo` 一次都没发生。
- [ ] 迁移只做 expand 时，回退到 N-1 镜像后应用能正常读写。
- [ ] App 运行中手工重跑知识 Job，确认先 `scale 0` 再跑 Job，不出现 `Multi-Attach error`。

阶段二：

- [ ] 滚动更新期间持续 `curl /smart-bot/ready`，失败次数为 0。
- [ ] 更新期间正在进行的问答不中断（`terminationGracePeriodSeconds` + `preStop` 生效）。
- [ ] 两个副本分布在两个节点时仍能正常挂载（这验证了 media 卷真的不再依赖 RWO）。

阶段三：

- [ ] fingerprint 变更时，新旧版本可同时存活超过 10 分钟，各自 `/ready` 均 200。
- [ ] 切换后回退镜像，旧版本继续正常检索，无需重建索引。

## 8. 明确不做什么

- **不把 `titu-assistant-var` 整块改成 RWX。** `accessModes` 不可变，要删 PVC 重建并迁移数据；Longhorn RWX 走 share-manager + NFSv4，小文件性能差；且 SQLite 在 NFS 上文件锁不可靠。正确做法是拆卷，不是换模式。
- **不引入 Argo Rollouts（现阶段）。** 金丝雀需要两个版本能同时服务，而 B4 决定了 fingerprint 变更时做不到；`Recreate` 下金丝雀也没有意义。等阶段三完成、指标补齐后再评估，那时 Argo Rollouts 的 `AnalysisTemplate` 才能接上真实信号。
- **不追求数据库零停机。** 迁移耗时本身就在窗口里，`CREATE INDEX CONCURRENTLY` 可以缓解大表，但不是本项目当前的主要矛盾。
