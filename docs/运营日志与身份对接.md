# 运营日志与身份对接

## 当前发布范围

本版保留平台自动身份接入契约，不新增免登录入口，也不替换平台账号密码系统。客服正式接入只使用后台确认的企业和用户身份。`/widget/demo` 与独立 `/chatbot` 的手动凭证界面仍作为联调入口；正式平台的 iframe 桥接不要求用户手工填写凭证。

## 前后端接入责任

平台后端提供与业务页面同源的 `GET /api/assistant/token`。读取现有已登录服务端会话，从中获取企业 ID 和用户 ID，调用 `app.core.issue_token(secret, tenant, user, lifetime=3600)`，返回 `{"token":"..."}`。未登录返回 401；响应使用 `Cache-Control: no-store`。不得使用浏览器传入的企业或用户 ID 直接签发身份，签名密钥仅放平台后端和客服后端。

平台前端加载客服 `/iframe.js`，可通过 `data-auth-url` 指定同源身份接口。现有脚本获取凭证并以限定来源的 postMessage 传入 iframe；凭证不放 iframe URL，不传递账号密码。平台登出或切换账号时调用 `SmartTITUEmbed.reset()`，清理旧用户客服状态。身份接口应支持到期重新签发。

客服后端验证签名、有效期、企业和用户；数据库查询使用企业、用户和会话共同限定归属。`FRAME_ORIGINS` 配置平台准确来源；浏览器跨域调用时另配 `CORS_ORIGINS`。平台后端适配接口不在本仓库内，不能仅嵌入 iframe 就获得网站登录身份。联调必须使用两个不同用户验证会话隔离、退出、账号切换和过期刷新。

## 标识如何关联

| 字段 | 含义 |
|---|---|
| timestamp | 默认北京时间，包含时区、日期和毫秒 |
| http_request_id | 每个 HTTP 请求编号，通过 X-Request-ID 返回 |
| request_id | 每条聊天消息编号，重试同一消息时沿用；聊天请求同时作为 HTTP 请求编号 |
| tenant_ref / user_ref | 使用 AUTH_SECRET 做 HMAC 后的企业和用户标识；日志不保存原始账号 |
| session_ref | 会话 ID 的 HMAC 标识；同一用户多段历史会话分别关联 |
| window_id | 随机窗口编号，经 X-Widget-ID 传递；每次页面加载重新生成，不是设备指纹 |
| question_category | 基于规则的粗粒度业务标签，例如 billing_payment、invoice、model_api；不代替模型判断 |
| intent | 工作流分类，例如 knowledge、image、greeting、handoff |

同一用户不同电脑或多个标签页可以有不同 window_id，也可能主动打开同一段会话；窗口不等于用户，会话也不等于窗口。window_id 是不可信的辅助排查标识，不参与权限校验。多个用户共用 demo/tester 凭证会被识别为同一个用户；正式隔离必须依赖平台真实登录身份。

日志按日期统一保存，不按用户拆成大量小文件。不同用户的日志可由运维按脱敏标识筛选，但日志文件本身只供服务器运维访问；不提供给客户端浏览，也没有面向客户的日志查看 API。聊天数据权限隔离由现有后端校验保证，日志关联字段本身不是权限控制。

## 文件位置和保留规则

默认目录为项目的 `var/logs/`，企业容器内为 `/ai_customer/var/logs/`，通过现有项目挂载持久保存。可使用 `LOG_DIR` 指定其他可写目录；覆盖后应同步调整查询命令的 `--directory`。

文件名示例：`app-2026-10-27-12345.jsonl`。问答请求每行一个完整 JSON，四个顶层字段为“时间、输入、处理流程、输出”；不再为同一问答逐节点写多条 JSON。其他系统和非问答访问事件仍逐条记录，另同步输出到容器日志。默认时区 `LOG_TIMEZONE=Asia/Shanghai`，保留 `LOG_RETENTION_DAYS=30` 天；切换到新日志日期时清理保留期外的自有日志文件。不是固定在午夜运行的定时任务；服务没有新日志时，旧文件不会主动清理。

每个工作进程分别写文件，避免多进程同时轮转同一个文件。每份文件约 20 MiB 轮转，每进程每天保留当前文件和最多 4 份大小轮转备份；高流量时同一天较早日志可能先被覆盖。多次进程重启会增加当天文件数量，不能将这个限制当作整个目录的磁盘总上限。应监控磁盘空间，较大规模时由运维接入集中日志采集和统一保留策略。

新建日志目录权限为 0700，日志文件为 0600。若目录无写权限或写入失败，服务保留容器标准错误中的日志并提示存储故障；需要修复目录权限或磁盘空间。`var/` 已在 Git 忽略列表内，不提交运营日志。

## 记录哪些事件

- `http_completed`：接口模板路径、状态码、是否完整结束、耗时；不记录查询参数和未知原始路径。健康检查成功不逐条记录，避免刷屏；失败仍记录。
- `session_created`、`chat_started`、`chat_cache_hit`、`chat_completed`、`chat_failed`：会话、消息处理、幂等缓存命中和最终业务结果。
- `question_classified`：工作流意图、历史消息条数。
- `retrieval_completed` / `retrieval_failed`：命中数量、内部知识 ID、向量分数、阈值、标题匹配、重排分数、耗时和失败类型。
- `retrieval_model_started` / `retrieval_model_completed` / `retrieval_model_failed`：分别记录 embedding 和 rerank 的请求耗时及失败类型，保留错误包装前的上游状态。
- `model_request_started` / `model_request_completed` / `model_request_failed`：模型请求耗时、输入消息条数、响应长度及接口错误分类。
- `model_finish`、`model_usage`：模型提供时记录停止原因、是否达到输出上限及 token 用量，不记录原始文本。
- `answer_validation_completed` / `answer_validation_failed`：格式及引用校验结果。
- `generation_completed` / `generation_failed`：生成阶段汇总，含历史消息条数和证据数量。
- `service_started` / `service_stopping`：服务生命周期。

错误分类包括 timeout、connection、upstream_http、invalid_json、answer_schema、citation_schema、citation_validation、image_validation、empty_answer、response_size、unexpected。记录可识别的异常类型和上游 HTTP 状态，不记录异常原文或完整堆栈，避免带出密钥、响应正文及地址参数。未知错误先以 unexpected 定位阶段，再在受控环境复现。

普通运营日志不记录问题原文、回答原文、聊天历史、Authorization、账号密码、签名密钥和原始模型响应；下文的临时调试正文采集为独立、显式开启的功能。问题字数、粗粒度类别、脱敏关联标识可用于统计。聊天原文仍按原有业务数据库及会话保留规则保存；需要回看时必须走已有权限控制，不能靠日志绕过。

## 排查命令

在服务器项目目录执行：

```bash
# 查看今天日志（日期按 LOG_TIMEZONE 选择）
python3 scripts/query_logs.py --date 2026-10-27

# 用浮窗“反馈问题”中复制的问题编号查询整条链路
python3 scripts/query_logs.py --request-id msg-替换为完整编号

# 只看失败、降级及警告
python3 scripts/query_logs.py --date 2026-10-27 --errors

# 筛选单个会话或窗口
python3 scripts/query_logs.py --session-ref 替换为日志中的会话标识
python3 scripts/query_logs.py --window-id window-替换为完整窗口编号

# 按问题类别筛选
python3 scripts/query_logs.py --question-category billing_payment
```

查询按文件顺序输出，多个进程或大小轮转文件的结果不保证全局时间排序；可根据新格式的“时间”或旧格式 timestamp 分析。不要把含账号或密钥的内容放进请求编号。

若页面失败而诊断命令偶尔成功，先用问题编号查看：

1. retrieval_completed 是否 matched=true，evidence_count 是否大于零。
2. model_request_failed 是否 timeout、connection 或上游 HTTP 错误。
3. model_finish 是否 length，是否输出截断导致 invalid_json。
4. answer_validation_failed 是否引用 ID、图片 ID 或格式校验失败。
5. history_messages 是否随长对话增长，generation 的耗时是否明显增加。
6. 是否出现 chat_cache_hit：同一 request_id 会复用已有结果；新一次提问应使用新编号。

SSE 或普通聊天可能以 HTTP 200 返回“建议其他问题”的业务降级结果，不能只监控 HTTP 5xx。应以 chat_completed 的 outcome/reason 统计回答成功率、无答案率、生成失败率，并结合检索与模型耗时、上游 429/5xx、限流和磁盘告警。

本次增加诊断日志，不改变相似度门槛，不放宽知识和图片引用校验，也不自动重试模型或直接用原文绕过生成失败。先根据实际错误确定修复方式，避免盲目扩大超时和重复请求模型。

## 部署生效

服务器拉取 main 后重启应用即可加载挂载目录中的 Python 和前端改动：

```bash
cd ~/ai_customer
git pull --ff-only origin main
docker restart ai_customer-assistant-1
```

浏览器强制刷新。现有 PostgreSQL、MinIO、Milvus 配置不变，无需重新入库或重建镜像。应用默认以现有用户写入项目 var/logs，如无法创建目录，先按容器运行用户修复宿主机目录权限，不能使用 chmod 777。

## 命中知识却没有回答的节点排查

默认普通日志已有模型请求、引用校验和最终业务状态。现在增加最终校验、页面响应准备、流式发送完成/中断节点，并支持中文排查报告：

```bash
python3 scripts/query_logs.py --request-id msg-完整问题编号 --report
```

若需要看到用户实际输入、命中正文、模型原始输出和最终对外回复，先开启独立的临时调试正文采集，再复现新请求：

```bash
cd ~/ai_customer
python3 scripts/configure_debug_logging.py enable --days 3
sh scripts/enterprise.sh start
```

该命令会备份 .env、添加 LOG_DEBUG_CONTENT=true 和保留天数。新增环境变量必须重建应用容器；单纯 docker restart 不会更新容器环境。enterprise.sh start 仅重建 assistant，不启动其依赖 PostgreSQL 等服务。旧请求没有采集的原文无法靠日志补录。

复现后复制窗口的完整问题编号：

```bash
python3 scripts/query_logs.py --request-id msg-完整问题编号 --report --debug-content
```

新请求的报告直接美化输出一份完整 JSON。“处理流程”数组按发生顺序包含输入、检索、Embedding/重排、模型生成、JSON/知识引用/图片校验、最终内容校验、问答保存、回复准备和发送节点；“输出.失败节点”标出第一个记录到的失败节点。旧格式日志仍支持原来的节点报告。它不会把 HTTP 200 当作回答成功，也不会把“服务端发送完成”当作“浏览器已显示”。如果后台回答和发送都完成但页面没有显示，接着检查浏览器 Network 中的 SSE complete 帧和 Console 错误。

独立 `debug-YYYY-MM-DD-PID.jsonl` 文件对每次新问答只写一条完整 JSON。输入包含实际问题；处理流程包含命中正文、模型输入、模型原始返回和校验上下文；输出包含最终响应及失败节点。普通 app 文件和容器 stdout 只保留同样结构的元数据摘要，不写正文。读取时使用 --debug-content，会优先选取完整正文，避免同时输出元数据摘要和正文两份。每个正文片段最多16000字符，超过会标记“已截断”；最多保留80个节点及12个正文片段，达到上限标记“流程已截断”。

调试正文属于受限诊断数据，可能包含客户业务内容、历史聊天和系统提示。保存前替换已知环境密钥值、Bearer 凭证和部分敏感 URL 字段，但这是尽力脱敏，不能保证用户自由文本中的所有敏感信息都被识别。目录和文件权限、访问范围与运营日志一样受限，默认保留3天。不会返回给浏览器，也不自动上传外部日志服务。采集开关保持开启时会继续采集，应在排查后关闭：

```bash
python3 scripts/configure_debug_logging.py disable
sh scripts/enterprise.sh start
```

关闭不会立即删除已采集的调试文件；普通运营日志在新日志日期继续按调试保留期清理旧 debug 文件，停机且没有新日志时不会主动清理。需要查找包含某个节点的整条请求时可使用（新格式仍输出整条JSON，不拆分）：

```bash
python3 scripts/query_logs.py --request-id msg-完整问题编号 --event model_input --debug-content
```

### 整条请求一次落盘

记录在问答结束后一次写入；HTTP流式请求会等发送结束或中断，确保发送结果也在同一对象中。并发请求使用独立缓冲区，线程间仅共享所属请求的缓冲区。客户端取消后写入已发生节点和取消结果，不再追加后台晚到结果。进程被强制结束时可能来不及写入整条记录；此时仍应结合服务启动/退出和系统日志排查。旧日志不回写，新格式只对更新后的新问答生效。这里的“处理流程”记录程序执行步骤，不是模型内部思维链。

## 模型输出格式恢复

默认向模型接口请求 `response_format: {"type":"json_object"}`，仍由服务端校验字段、引用和图片。只有接口以 400/422 明确拒绝 response_format 时，自动去掉该参数重试；其他 HTTP 错误或超时不因此重试。可在 `.env` 设置 `MODEL_RESPONSE_FORMAT=text` 关闭 JSON 模式；修改环境后需重新创建 assistant 容器。

模型返回 JSON 语法错误（包括重复字段）时，最多进行一次格式修复生成，使用本轮问题、证据和错误返回，不携带旧主题历史。修复内容与正常答案执行相同的字段、引用和图片检查，不直接拼补文本或提取未校验的答案。伪造引用、未登记图片等校验错误不自动放行，也不触发格式修复。修复会增加一次模型调用的等待和用量。

同一个请求 JSON 的处理流程包含“回答格式修复开始 / 成功 / 失败”。修复成功时，输出标注“已恢复异常”；最终格式或引用校验失败时 reason 为 `model_invalid_response`，模型连接、超时等调用故障仍为 `model_unavailable`。启用调试内容后，两次模型输入输出均记录在该请求的处理流程内。格式修复耗尽后仍返回原有友好提示，避免展示错误内容。
