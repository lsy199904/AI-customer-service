# 初始化 Job 说明——服务与数据初始化

本文件对应清单 [`90-init-job.yml`](90-init-job.yml)。初始化 Job 是应用在 K8s 上启动前的**一次性准备任务**：它不对外提供任何服务，跑完即退出；只有它成功完成后，Deployment 里的应用容器才能真正就绪。

## 一、为什么需要单独的初始化 Job

应用镜像是"纯静态"的：里面只有代码、正式知识文档和图片登记文件，**不含任何运行时数据**——既没有 PostgreSQL 的表结构，也没有 Milvus 的向量集合，更没有已入库的知识索引。

而应用启动后立刻就要读写会话表、检索知识向量，如果数据库里没有对应的表和集合，服务只会反复崩溃。所以部署采用"两段式"：

1. 先跑初始化 Job：建表、入库、自检；
2. Job 成功后再启动/更新应用 Deployment。

Job 与应用使用**同一个镜像、同一份 ConfigMap 和 Secret、同一个 PVC**，区别只在启动命令：Job 执行初始化命令序列，应用容器执行 `python -m app.server`。这样保证"初始化时检查通过的环境"与"运行时使用的环境"完全一致，不会出现配置在两边不同步的问题。

## 二、Job 做了什么

一条命令按顺序串联三个阶段，用 `&&` 连接——**前一阶段成功才会进入下一阶段，任一阶段失败整个 Job 立即失败**：

```
python -m app.deployment initialize && python manage.py ingest && python manage.py doctor --models
```

三个阶段分别回答三个问题：库和服务的"骨架"是否就绪（阶段一）、知识"数据"是否入库（阶段二）、成品是否真的可用（阶段三）。

### 阶段一：`app.deployment initialize`——前置检查与服务结构初始化

这是整个初始化中最严格的一步，按顺序执行五组检查，全部通过后才做两次写入。设计原则是"**先检查、后动手**"，任何一项不满足都直接失败，绝不带着问题继续建表。

**配置检查**：确认环境变量齐备——数据库连接串、向量后端必须是 milvus、部署标识 `DEPLOYMENT_ID` 等必须存在。缺项说明 ConfigMap/Secret 没配对，直接失败。

**PG 连接与部署隔离检查**：连上目标业务库后，判断这个库"能不能用"：

- 如果库里已有本方案标记表（记录着上次部署的标识与 Milvus 连接信息），则逐项比对：部署标识、Milvus 地址、库名、集合前缀必须与本次环境变量完全一致。不一致说明这个库属于**另一套部署**，继续写入会互相覆盖，拒绝初始化；
- 如果没有标记表，但库里已存在客服或知识的表，说明这是一个"有数据但不属于任何已知部署"的库，同样拒绝；
- 只有确认是空库（或属于本部署自己的库），才检查账号是否有建 schema 所需的权限，然后放行。

这一步的目的：**多个环境的部署共用同一个 PG 实例时，靠部署标识互相隔离，杜绝误写别人的库**。

**文档与图片检查**：扫描镜像内 `../../../../../knowledge_sources` 目录下的全部 Word、PDF、Markdown、TXT 文档（没有可入库文档直接失败），逐个解析成文本块并统计数量；同时校验所有被文档引用的图片编号都已在 `data/media.json` 登记（包括 PVC 里已生成的 PDF 配图）。缺失登记即失败——否则入库后答案会引用"死图"。

**模型接口检查**：用一句固定文本真实调用外部模型接口，不是 ping 一下地址：

- 调 Embedding 接口，拿到返回的**向量维度**（后面校验 Milvus 集合时要用）；
- 再依次调用 Rerank 和 LLM 接口各一次，验证 URL、密钥、模型 ID、协议和网络连通性，鉴权失败或超时都会在这一步暴露，而不是等到上线后用户提问时。

**Milvus 连接检查**：列出目标 Milvus 数据库里的集合：

- 若已有以本部署集合前缀开头的集合但不属于本部署，拒绝（前缀冲突）；
- 若本部署集合已存在，比对其中向量字段维度与刚才 Embedding 返回的维度，不一致说明 Embedding 模型换过而集合没换，拒绝。

**全部检查通过后，才执行两次写入**：

- **登记部署归属**：在 PG 行级锁保护下创建 `assistant` schema 和部署标记表，写入本次部署的标识信息，完成"认领"；
- **服务数据结构初始化**：创建客服会话表、知识表（`assistant` 与 `knowledge` 两个 schema）以及 LangGraph 工作流的持久化检查点表。建表语句全部幂等（存在即跳过），**重复执行不会破坏已有数据**。

此阶段结束时，骨架就绪，但**还没有写入任何向量**。

### 阶段二：`manage.py ingest`——知识数据初始化

把镜像内 `../../../../../knowledge_sources` 的正式文档转换成可检索的语义索引，数据落在两处：PG 存元数据、原文、分块与缓存，Milvus 存向量。核心流程：

**增量识别**：每个文档按"内容哈希 + Embedding 配置指纹 + 解析器版本"计算修订号，与已入库记录比对——内容没变的文档直接跳过，只有新增和变化的文档才会重新处理。所以同一镜像重复跑 ingest 是安全的，换新镜像（带了新知识文档）后重跑也只处理增量。

**解析与切片**：按配置的块大小和重叠度把文档切开；PDF 开启配图提取时，把图片写入 PVC 的 `pdf_media` 目录并登记，供答案引用。

**向量化（带缓存）**：先查 PG 里的 Embedding 缓存表——同一 Embedding 版本下相同文本直接复用已有向量，未命中的才分批（每批 8 条）调用外部 Embedding 接口，并把结果写回缓存。重跑时大部分文本直接命中缓存，调用量很小。

**发布顺序保证可回退**：先把手素向量的分块全部 upsert 到 Milvus，**再**在 PG 事务里更新"当前修订版"指针并递增索引代数。指针提交之前，线上检索的过滤条件仍命中旧版本——即使发布中途失败，已上线服务的旧知识完全不受影响。全部解析和外部调用都成功后才会发布，不存在"发布一半"的状态。

**一致性兜底**：本次所有向量维度必须一致（混入不同维度整体拒绝发布）；检测到入库期间索引被并发修改时，放弃本次发布要求重试。

阶段完成后的标志：Milvus 中出现以 `MILVUS_COLLECTION` 为前缀的集合且有数据；PG `knowledge` schema 中文档、分块、修订记录表有数据。

### 阶段三：`manage.py doctor --models`——成品体检

前两步证明"骨架建了、数据写了"，这一步以**与应用完全相同的代码路径**做端到端自检，确认成品真的可用：

- 数据库连通，会话与知识表可正常访问；
- 工作流检查点持久化正常；
- Milvus 中存在当前集合，且活动知识数量大于零（防止"表建好了但知识是空的"这种静默问题带上生产）；
- `--models`：再次实测 Embedding 等模型接口并核对维度。

任一项失败，Job 以失败结束。通过即代表：应用容器接下来启动时依赖的一切（库、集合、知识、模型）都已就绪。

## 三、失败怎么办

Job 配置为**失败不自动重试**（`backoffLimit: 0`）——因为失败原因几乎都是配置或外部依赖问题，盲目重试没有意义，需要人工看日志、修正后重建 Job：

```bash
kubectl -n app-zone logs job/titu-assistant-init        # 看失败在哪个阶段、什么原因
# 修正 10-configmap.yml / 20-secret.yml / 外部服务后：
kubectl -n app-zone delete job titu-assistant-init --ignore-not-found
kubectl apply -f 90-init-job.yml
```

三个阶段都是幂等的：表是"存在即跳过"，ingest 只处理增量，体检是只读的，所以**修正后直接重跑即可，不会产生重复数据**，也不需要清理半成品。

常见失败原因按阶段对照：

| 阶段 | 典型原因 |
|---|---|
| 一（initialize） | 数据库账号缺 CREATE 权限；目标库非空且不属于本部署；Milvus 集合前缀冲突；Embedding 维度与既有集合不一致；模型接口 401 / 超时 / URL 填错 |
| 二（ingest） | 文档引用的图片未登记；Embedding 接口限流或中断 |
| 三（doctor） | 知识数量为 0（ingest 实际没入库）；Milvus 集合缺失 |

Job 无论成功失败，记录都保留 24 小时（`ttlSecondsAfterFinished: 86400`）供排查，之后自动清理。

## 四、与其他部分的边界

- **不创建基础设施**：PG 实例和 Milvus 实例必须已经存在且可达（见上级目录的前置条件），Job 只是在已有的库里建 schema 和表、在已有的 Milvus 库里建集合；
- **不迁移旧数据**：连接的是外部业务库，初始化不含历史数据迁移；
- **应用不做建表**：App 容器启动后只读写表和集合，不做任何结构变更，因此"先 Job 后 App"的顺序不能颠倒；
- **更新知识的固定套路**：把新知识文档打进新镜像 → 发版时重跑 init Job（其中 ingest 自动增量入库）→ 再滚动更新 Deployment。
