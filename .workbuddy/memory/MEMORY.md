# 项目长期约定

- 部署形态（2026-11-20）：当前阶段因工作量大、时间紧，暂不使用 Kustomize，改用 Kubernetes 原生 YAML 清单部署。生效清单位于 `deploy/k8s/dev`：`00-namespace.yml`、`10-configmap.yml`、`20-secret.yml`、`30-pvc.yml`、`40-job-db-migrate.yaml`、`50-job-milvus-init.yaml`、`60-deployment.yml`、`70-service.yml`。**注意 `75-ingress.yml` 并不在仓库中**（只在 `deploy/k8s/dev/README.md` 里描述了规格，git 从未提交过该文件），写文档时不要把它当既有清单引用。**不引入发布脚本**（用户明确要求，`release.sh` 已删除）：发布顺序与环境要求全部写在 `deploy/k8s/dev/README.md`「发布步骤」——scale 0 → db-migrate Job → 知识 Job → 删 Job 等 Pod 退出 → apply Deployment → rollout status → Pod 内冒烟。命名空间在清单里写死 `app-zone`。旧 `deploy/k8s/base/` 与 `deploy/k8s/run-*.sh` 已清理，仓库不再保留 `kustomization.yaml`。
- 发布失败语义（2026-11-20）：Job 阶段失败时只 `kubectl scale --replicas=1` 把旧版本拉回，**不要** `rollout undo`（会退到更早的版本）；只有 apply 之后的失败才 undo。另：`kubectl scale` 不支持 `--ignore-not-found`（仅 `delete` 支持），必须用显式 `get deployment` 判断存在性，不要用 `2>/dev/null || true` 吞错。
- 镜像职责（2026-11-20，用户明确决策）：**app 镜像（`deploy/docker/app/Dockerfile`）是纯 Python 应用镜像，不打包 Flyway / Java / migrations**；数据库迁移只由独立的 `deploy/docker/db-migrate/Dockerfile` 镜像执行。K8s `40-job-db-migrate.yaml` 用 db-migrate 镜像，`60-deployment.yml` 与 `50-job-milvus-init.yaml` 用 assistant 镜像，两镜像同 tag 配套构建。曾出现过把 Flyway 内置进 app 的"单镜像方案"改动，已按用户决策回退。
- 构建网络（2026-11-20，实测）：国内**无法直连 Docker Hub**（`registry-1.docker.io` 8 秒超时）。db-migrate 的基底镜像需换源，已验证 `docker.m.daocloud.io/flyway/flyway:11.20.3-alpine` 可拉取（index digest `sha256:07f65a04ac518f3bf1c00a52dab46aa9649d931510860c6ac5363d6fb75e4c1b`，8 层 314.7 MB）并能完整构建出可用镜像；备选 `docker.1ms.run`。长期方案是把基底镜像中转进自有仓库 `ctt-repository-cn-guangzhou.cr.volces.com/smarttitu-assistant/`。命令行 `--flyway-image` / 环境变量 `FLYWAY_IMAGE` 覆盖，默认值仍保留上游 `flyway/flyway:11.20.3-alpine` 以保持可移植。
- 清单现状（2026-11-20）：`60-deployment.yml` 已**不含任何 Init 容器**（早期 `db-verify` 的 `flyway validate`、`knowledge-ingest` 均已移除），迁移与知识入库全部前移到独立 Job，发布顺序由人按 README 执行。当前镜像仓库为 `ctt-repository-cn-guangzhou.cr.volces.com/smarttitu-assistant/`（`smarttitu-db-migrate` / `smarttitu-assistant`），与 `build.sh` 默认的 `harbor.rd.dsi/smarttitu` 不同，构建需覆盖 `REGISTRY` / `IMAGE_NAME`。各镜像构建指南见 `deploy/docker/{app,db-migrate}/README.md`。
- 对外访问方式（2026-11-20，用户先后要求「用 NodePort 不用 Ingress」→「不要改我的 Deployment，回退」→「先放弃 NodePort 采用 Ingress」，**最终定为 Ingress**）：`70-service.yml` 为 `ClusterIP:8201`（`targetPort: http`，容器名 http=8201），对外由 `75-ingress.yml` 提供——host `titu-assistant.k8s.ird`、`ingressClassName: nginx`、`cert-manager.io/cluster-issuer: internal-cluster-issuer`（secret `titu-assistant-tls`，实测 11s 签出 READY=True）、`proxy-buffering: "off"` + `proxy-read/send-timeout: "3600"`（SSE 必需）、`ssl-redirect: "true"`。已 apply 并实测：`curl -k -H 'Host: titu-assistant.k8s.ird' https://10.180.158.31/smart-bot/ready` → 200，`/smart-bot/` 与 `/` → 401（到应用），HTTP 80 → 308。集群 80/443 由内置 `rke2-ingress-nginx`（DaemonSet+hostNetwork，8 节点）提供，与 grafana/longhorn/prometheus/keycloak 同一模式。**Deployment 保持原样，禁止加 `hostPort`**（曾加过被用户要求回退）。NodePort 走不通的根因留档：Cilium `kubeProxyReplacement: true` + `HelmChartConfig rke2-cilium` 的 `devices: eth1`，nodePort 的 BPF 不覆盖 eth0（外网 RST，`/proc/net/tcp` 无 `:75F9`）。**Ingress 不能直接用 `http://<节点IP>/` 访问**（host 绑定，实测 404）；要 IP 访问只能用 `nginx.ingress.kubernetes.io/server-alias` 注解补节点 IP（已实测 404→200），但主 Ingress 有 `ssl-redirect: "true"` 会 308 到 `https://<IP>/` 而证书 SAN 只有域名 → 告警；不要用无 host 的 catch-all 规则（会抢占共享 ingress-nginx 的全局默认后端）。
- 配置与文档口径（2026-11-20，README 重写时核对）：**唯一配置模板是 `docs/app.env.example`**；根 `.env.example` 已不存在，因此 `manage.py init` 与 `scripts/configure_external.py`（以及 `tests/test_external_deployment.py`）都不可用，`scripts/dev.sh` 也仍指向根 `compose.dev.yaml` 与根 `manage.py`（实为 `deploy/compose/compose.dev.yaml`、`database/milvus/manage.py`）。`.env` 只由 `manage.py` 读取，`python -m app.server` 不自动加载；本地最小可运行配置 = `AUTH_SECRET`(≥32B) + `ANSWER_MODE=extractive` + `RETRIEVAL_BACKEND=lexical`。写文档时默认值以 `app/core.py:Settings`、`app/rag.py:RAGSettings` 为准（如 `RETRIEVAL_TIMEOUT_SECONDS` 代码 15 / 生产 60，`RERANK_MIN_SCORE` 代码 0.6 / 生产 0）。
